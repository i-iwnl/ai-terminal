## 2026-07-29 - Phase 1 / PR 1: 既定値を src/shared へ寄せる

### 実施内容

- `src/shared/defaults.ts` を新設し、`DEFAULT_THEME` / `DEFAULT_WEBHOOK` / `DEFAULT_CONFIG` を移した
- `src/main/config.ts` の自前定義を削除し、shared を参照するようにした
- `src/renderer/src/lib/defaults.ts`（#25 で作った暫定の置き場）を削除し、
  `App.tsx` / `SettingsWindow.tsx` は `@shared/defaults` を直接見る形にした
- `config.ts` からの再エクスポートは作らず、テストも唯一の正から直接 import するようにした
- **`coerceConfig({})` が `DEFAULT_CONFIG` と一致することを単体テストで固定した**
- 検証: `make check`（unit 76）/ `make e2e`（38 passed）/ `make e2e-lint`（PASS=279 FAIL=0）
- **`screenReaderMode` を `coerceConfig` から外して、新テストが赤くなることを確認した**

### 設計判断

- **再エクスポートを作らない。** `config.ts` から `DEFAULT_CONFIG` を再エクスポートすると
  同じものへの経路が2本になる。テスト側の import を1行変えるほうが安い
- Renderer 側の `FALLBACK_CONFIG` という名前をやめて `DEFAULT_CONFIG` に統一した。
  「フォールバック」と「既定値」が別物に見えていたのが、そもそも二重化を許した一因

### 教訓（該当する場合）

- **型が守ってくれない二重化がある。** 設定項目を増やすとき、`AppConfig` と `DEFAULT_CONFIG` は
  型で守られるが、**`coerceConfig` への追加漏れは型では検出できない**
  （返り値の型は満たしたまま、その項目だけが常に undefined になる）。
  空オブジェクトを食わせて既定値と一致するかを見る1行で、そこを機械化できた
- **「見た目の変化ゼロ」は `git status docs/images/` で確認できる。**
  主張するだけでなく、画像に差分が出ていないことを実際に見た

### 次に再開するとき最初に読むべきこと

- **PR 1 は完了。** 次は Phase 1 の PR 2（`:root` にトークンを宣言だけ追加。使用箇所ゼロ、値は現行 hex と 1:1）
- **PR 2〜4 は画像0枚、PR 5 で12枚**。この境目を崩さないことが Phase 1 の設計そのもの

### 実施内容

- `styles.css` の先頭に `:root` のトークン群を追加した。**使用箇所ゼロ**（宣言だけ）
- 現行の色を棚卸しした結果 **33種類**あり、面だけで8種類の近いグレーが混在していた
- 値はすべて現行のリテラルと 1:1 にした。PR 5 で変える予定のものには、
  変更後の値と理由（コントラスト比）をコメントで併記した
- 4段に畳めない中間色には**移行用トークン**（`--surface-tabbar` 等）を用意し、
  PR 5 で削除する前提であることを明記した
- 単体テスト `test/unit/css-tokens.test.ts` を追加した
- 検証: `make check`（unit 79）/ `make e2e`（38 passed）/ `make e2e-lint`（PASS=279 FAIL=0）/ 画像 0枚

### 設計判断

- **移行用トークンを作ることを選んだ。** 面を最初から4段に畳むと、その時点で見た目が変わり
  PR 3 が「値据え置き」を名乗れなくなる。近い色をいったんトークン名として温存し、
  PR 5 でまとめて畳む
- **トークン名は「用途」ではなく「目標の段」で付けた**（`--surface-sidebar` ではなく `--surface-0`）。
  用途で名付けると PR 5 で名前ごと変わり、値の変更と改名が混ざる

### 教訓（該当する場合）

- **「値は現行と 1:1」は主張ではなく検査にできる。**
  宣言した色が CSS 本体で実際に使われている値かを機械で確認するテストを書いた。
  `--surface-0` の値を1文字変えて赤くなることを確認済み。33種類の近い色を目視で守るのは無理
- 同じ値に2つのトークンが付くと置換のときに揺れるので、**重複も検査した**。
  偶然一致している3組（`#232323` / `#333333` / `#666666`）は理由付きで許容リストに入れてある

## 2026-07-29 - Phase 1 / PR 3: 面と境界を変数へ置換する

### 実施内容

- 面（background）と境界（border 系）、影を `var(--...)` へ置換した。**値は据え置き**
- 検索バーの浮いた面（`#2a2a2a`）が区切り線と同値だったため、`--surface-float` を追加した
  （用途が違うので別トークンにし、重複の許容リストに理由付きで入れた）
- 単体テストに2つ足した:
  - `var()` が参照しているトークンがすべて宣言されていること（**タイプミスは CSS では黙って無視される**）
  - 宣言した色が「未置換ならリテラルが実在／置換済みなら参照されている」こと（段階的な置換に対応）
- **`scripts/verify-css-substitution.mjs` と `make css-substitution-check` を新設した**
- 検証: `make check`（unit 81）/ `make e2e`（38、S32 が1回 flaky）/ `make e2e-lint`（PASS=279）/ 画像0枚

### 設計判断

- **「値据え置き」を証明する仕組みを作った。** トークンを機械的に展開して HEAD の CSS と
  文字列比較する。結果は**完全一致**。目視でも E2E でも画像でも「色が少し違う」は検出できないので、
  これが唯一の担保になる
- 値を変える PR（PR 5）ではこのスクリプトは当然落ちる。**`make check` には入れず、独立した target にした**

### 教訓（該当する場合）

- **`var()` のタイプミスは CSS では黙って無視され、その宣言だけが効かなくなる。**
  ビルドも E2E も通ってしまう。`var(--surface-tabbar)` を `--surface-tabber` にして、
  2つのテストが赤くなることを確認した
- **検査は置換の進行に合わせて育てる必要がある。** PR 2 で書いた「宣言した色はリテラルとして
  実在する」は、置換した瞬間に全部落ちる。「未置換ならリテラル／置換済みなら参照」に
  書き換えて、段階的な移行のあいだも意味を持つ形にした
- **「見た目が変わっていない」は主張ではなく証明できる。** 画像の差分ゼロは弱い証拠
  （経過時間が毎回変わるので、そもそも画像は毎回バイト差が出る）。トークンを展開して
  元の CSS と一致することを見るのが本当の担保

## 2026-07-29 - Phase 1 / PR 4: 文字色・状態色・アクセント・サイズ・余白を変数へ置換する

ブランチ: `refactor/css-tokens-type-and-space`（`main` = `6a2fa78` から分岐）

### 実施内容

- **`styles.css` 本体から色のリテラルが完全に消えた**（148行を置換）。文字色9種・アクセント・
  状態色5種・通知色・フォントサイズ6段・行間・余白（4px グリッド）・角丸を `var(--...)` へ。**値は据え置き**
- 置換は手作業ではなく使い捨てスクリプトで機械的に適用し、差分を目視で検分した
  （`:root` とコメントには触らない・寸法は対象外、という規則をコードで表現した）
- `make css-substitution-check` が **PASS**（HEAD と完全一致 = 見た目の変化ゼロ）
- 単体テストを「置換が完了した後の形」に強めた:
  - 旧「未置換ならリテラル／置換済みなら参照」を廃し、**未参照の色トークンはゼロ**を要求
  - **本体に色のリテラルが1つも残っていない**を追加（トークンを迂回した直書きの再混入を止める）
  - 色以外の未参照トークン（`--lh-tight` / `--sp-6`）は**理由付きの許容リスト**に載せた。黙って増やせない
- `scripts/verify-css-substitution.mjs` が比較前にコメントを落とすようにした
- ルート `CLAUDE.md` に `make css-substitution-check` と「置換と値の変更を混ぜない」規約を追記した
  （PR 3 で target を作ったのに唯一の正へ書いていなかった）
- 検証: `make check`（unit 100）/ `make e2e`（39 全緑・flaky 0）/ `make e2e-lint`（PASS=286 / FAIL=0）/
  `lint-skills`（PASS=87 / FAIL=0）/ 画像0枚

### 設計判断

- **4px グリッドに乗らない余白（2 / 3 / 6 / 10 / 14 / 18 / 20px）と `border-radius: 4px` は
  リテラルのまま残した。** グリッドへ畳むのは値の変更で見た目が動く。置換の PR に混ぜると
  「画像が変わった理由を分離できない」という Phase 1 の前提そのものを壊す
- **寸法（幅・高さ・線幅）は余白トークンの対象にしない。** `width: 8px` のドットと
  `gap: 8px` の余白が同じトークンを共有すると、PR 5 で尺を動かしたときにドットまで太る
- **`--lh-tight` / `--sp-6` は使用箇所ゼロのまま残した。** 尺の段を飛ばさないため。
  ただし「宣言だけあって使われない」を放置しないよう、テストの許容リストに理由込みで固定した
- **検証スクリプトからコメントを除外した。** 置換すると「既定色 #666 のまま」のような
  コメントが嘘になるが、直すと比較が落ちるため直せない、という板挟みが起きていた。
  コメントは描画に影響しないので落として良い

### 教訓

- **「コメントを比較対象から外す」は検査を弱めるので、弱まっていないことを実際に確かめた。**
  宣言を丸ごとコメントアウトする改変（`/* padding: ... */`）を注入したところ、
  宣言の行そのものが消えるため従来どおり検出できた。**確かめずに除外していたら、
  「消したのに気づかない」穴を自分で開けていた**
- **今周は負の対照を5件まとめて流した**（値の変更・宣言のコメントアウト・未参照トークン・
  リテラル直書き・`var()` のタイプミス）。全件で赤を確認してから緑を報告している
- **検査は置換の進行に合わせて「強める」だけでなく「捨てる」必要がある。** PR 3 の
  「未置換ならリテラル／置換済みなら参照」は、置換完了後は**常に真になる無意味な検査**に変わる。
  残しておくと、通っていることが何も保証しないテストが1本増える

3. **PR 5 では `make css-substitution-check` が落ちるのが正しい。** 落ちたことを不具合と読み違えない。
