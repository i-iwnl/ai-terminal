### 設計判断

- **入力欄は1つのまま、確定先だけを分けた**（`editingTarget: 'tab' | 'pane'`）。
  タブのダブルクリックは `'tab'`、メニューの「ペイン名を変更...」は `'pane'`。
  `aria-label` も同じ値で出し分ける（**画面の語と、実際に変わるものを食い違わせない**）。
  入力欄を2つ作ると `.tab-bar__title-input` を見ている既存 spec（S26 / S46 / S69）が
  全部影響を受ける
- **識別と状態で引き先を分けた。** 見出し・プロバイダ色・ツールチップは代表 leaf
  （木の先頭）から。終了バッジ・`is-exited`・「あなたの番」には**触っていない**
  （それぞれ別の意味が既に決まっている。ここに混ぜると第三の意味が増える）
- **`renameTab` と `renamePane` で空文字の扱いを非対称にした。** タブ名は未設定が
  正常な状態なので「消して既定へ戻す」経路が要る。ペイン名は spawn 時の既定が
  常にあるので、空文字は「変更しない」で足りる

### 教訓

**1. 「赤くなるか」の確認で、キーが効いていないだけの偽の赤を除く。**

S86 の核心は「`Cmd+]` を押しても見出しが動かない」。だが**キーが1つも効いていなくても
この assert は通る**。そこで同じ spec の中に
`await expect(window.locator('.terminal-pane.is-active .pane-header')).toContainText('claude')`
を置き、**ペイン側は確かに移っていること**を先に固定した。

同型の穴をもう1つ塞いだ。プロバイダ色の往復を見るには**左右が別プロバイダである
必要がある**が、シェルタブを分割すると両方 shell になって色が動かず、検査が空振りする。
claude タブを分割し、さらに `headers.nth(0)` が `claude` / `nth(1)` が `zsh` であることを
spec 内で assert して、**検査が意味を持つ条件そのものを固定した**
（loop.md「検査は正しいが、その条件を踏んでいない」）。

**2. 起動直後にショートカットを押すと、無言で何も起きない。**

S86 の初版は `launchApp()` の直後に `Meta+Shift+C` を押していたが、**タブが1枚も
増えなかった**（受け取った文字列が初期シェルのプロンプトのままだった）。
設定の読み込みと初期シェルの spawn が終わる前に `new-claude-tab` が走ると、
エラーも通知も出ないまま何も起きない。**初期シェルのプロンプトを待ってから押す**。

**3. 意図した仕様変更で既存 spec が落ちたら、期待値だけ書き換えない。**

S26 の「空白のみ入力時に元のタイトルが維持される」が落ちた。これは Issue #131 の
完了条件そのもの（空文字で導出に戻す）なので、**spec のコメントと
`scenarios.yml` の note の両方に「いつ・なぜ変わったか」と、ペイン名側との
非対称の理由を書いてから**期待値を更新した。期待値だけ直すと、次に読む人には
「テストを通すために緩めた」ようにしか見えない。
