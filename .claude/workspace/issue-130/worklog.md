### 教訓

**1. 「存在しない」と書く前に、その機能を実際に使う経路を全部たどる。**

初版は「終了バッジはどこにも出ない」「永続的な状態表示が存在しない」と書いたが、
`useTerminal.ts:208-211` が `term.write('\r\n\x1b[2m[プロセスは終了しました…]\x1b[0m\r\n')` で
**終了したペインのスクロールバックに書き込んでいた**。出力はそこで止まるので、その行は
常に画面最下部にある。4人が独立に反証した。

同様に「`exit` を描画しているのは `TabBar.tsx` の1箇所」も誤りで、実際は**4箇所**
（`:335` aria ラベル / `:343` `is-exited` クラス / `:357` state-slot / `:443` バッジ）。
バッジだけ直すと語とマークがずれる。

**`grep` で1箇所見つけて満足しない。同じ値を読む箇所を全部数える。**

**2. 幅の見積もりは、CSS 定数から計算できるなら「実測が要る」で先送りしない。**

初版は「ヘッダ2要素は横幅が足りるか」を「実測が要る」として保留した。
だが `MIN_PANE_COLUMNS = 20`（`paneTree.ts:116`）と `padding: 0 var(--sp-2)`（`styles.css:1040`）から
**ヘッダ実幅 148.6px** は確定し、必要幅 208.7px（再開版 242.4px）も文字幅の実測で出る。
4人が独立に計算し、全員「入らない」に到達した。**保留した論点が、実は計画段階で決着できた。**

**3. 「A か B か」の二択で議論していたら、正解が third option であることを疑う。**

初版はリネームの入り口を「ヘッダか、タブバーか」の二択で議論していた。
5人全員が独立に**メニュー項目**へ到達した。しかも現状リネームは `TabBar.tsx:436` の
`onDoubleClick` だけで `AppAction` にも `menu.ts` にも無く、**キーボードから1手も到達できない
既存の WCAG 2.1.1 違反**だった。初版はその違反を2箇所目に複製する提案になっていた。

**4. 自動でできる道があるなら、手作業の UI を作る前に測る。**

ヘビーユーザーが `xterm.js` の `onTitleChange`（`src/` 全体で0ヒット）を指摘し、
「繋がればユーザーが1文字も打たずにペインが自分を名乗る。順序が逆」と書いた。
実際に測った結果は**塞がっていた**（tmux の `set-titles` が既定 off、`~/.zshrc` に
title を設定する `precmd` が無い）。**塞がっていることが分かったのが収穫**で、
これを測らずに手打ちの UI を作っていたら「なぜ自動にしなかったのか」が
記録に残らなかった。

**5. 既存の確定事項に抵触していないかを、`design-review.md` まで遡って確認する。**

初版の提案（タブバーの終了バッジを `some` にする）は `issue-56/design-review.md:81` の
「**全 leaf が終了したときだけ**出す」と正面から矛盾していた。しかも `TabBar.tsx:351-353` の

### 設計判断

- **`renamed` は明示フラグにした。文字列比較で判定しない。** `isResume`（`paneTree.ts:72-79`）が
  同じ問題に対して既に「`title` から文字列で判定しない」という結論を出しており、その理由が
  そのまま当てはまる。既定の `title` は `basename(cwd)` や分割時のリテラル `'zsh'` なので、
  **ユーザーがたまたま同じ文字列を打った場合と区別が付かない**。逆に履歴からの再開では
  既定値のほうがユーザー由来に見える文字列になるため、比較は両方向に化ける
- **`renameTab` -> `renamePane` の改名を、この Issue の中でやった。** レビュー（保守）は
  「挙動を1つも変えない単独 PR にせよ」と言っており、それが正しい。ただし
  **この Issue のテーマそのものが「タブの名前とペインの名前の混同」**で、その中で
  `renameTab` という名前の関数がペインを書き換えている状態を残すと、次に読む人が確実に誤解する
- **編集対象のペイン ID を `editingPaneIdRef` で持ち回る。** 確定時に `tabLeaf(tab)` で引き直すと、
  編集中に別のペインへフォーカスが移った場合（メニュー・通知クリック経由）に
  **入力欄に出ていた名前とは別のペインが書き換わる**
- **メニューからの編集開始は `registerRenameStarter`。** `Sidebar` の `registerPanelSwitcher` と
  同じ形。下書き文字列を App へ持ち上げると、タブの再描画のたびに入力途中の文字が失われる
- **`.pane-header` の `aria-hidden="true"` は維持した。** インタラクティブにしないので外す理由が
  無く、`aria-label`（完全版）との二重読み上げを避ける
- **CSS を1行も触っていない。** 画素検査で `docs/images/` 全枚数が 差0 だったことで実証済み

### 教訓

**1. 「赤くなるか」は、関門ごとに別々に確かめる。**

S85 は2つの関門を持つ（ヘッダが名前を出す / メニューに項目がある）。**両方を別々に潰して確認した。**

- `paneHeaderLabel` の分岐だけを Issue #130 以前へ戻す -> `Expected: "E2E-RIGHT-PANE" / Received: "zsh・demo-project"` で赤
- `menu.ts` の項目だけを消す -> `アプリケーションメニューに「ペイン名を変更...」が無い` で赤

片方だけ確認していたら、もう片方は「通ることの確認だけをした関門」になっていた
（loop.md「両端だけ固定して、真ん中が無テスト」）。

**`make e2e` ではなく `npm run build` + `npx playwright test S85` で回した。** loop.md が
禁じているのは「`src/` を壊したのに `out/` が古いまま単体で spec を叩く」ことなので、
**`build` を明示的に挟めば単体実行でよい**（`make e2e` は 2.5 分かかる）。

**2. 「その手がかりで気づける」と README に書く前に、その手がかりが更新されるかを確かめる。**

`README.md:299` は「分割で作ったシェルがエージェントの現在地とずれることがある
（**ペインヘッダの cwd 表示で気づける**）」と書いていたが、`useTabs.ts:175` の
`if (leaf.ptyKind !== 'shell') return;` により**エージェントのペインの cwd は
ポーリング対象外**で、起動時の値が凍結している。動く値と凍った値を並べても、
ずれには気づけない。**この周でヘッダを触るので、同じ周で直した。**

同じ理由で `README.md:283` の「アクティブなペインはペインヘッダの文言で分かる」も消した。
`.pane-header` にアクティブ状態を表す CSS 規則は1つも無く、文字列も（名前を付けるまで）
全ペインで同一。**存在しない手がかりが説明書に載っていた。**

**3. eslint の `react-hooks/exhaustive-deps` はこのリポジトリで有効になっていない。**

`// eslint-disable-next-line react-hooks/exhaustive-deps` を書くと
`Definition for rule was not found` で **lint が落ちる**。意図的に依存を絞るときは、
`useTerminal.ts:231` と同じく**コメントで理由を書く**（disable 指示子は書かない）。
