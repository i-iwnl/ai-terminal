## 4. ウィンドウの非アクティブ化（Cmd+Tab）でメニューが閉じない。**検証手段が無いので直していない**

### 症状

「+ ▾」メニューを開いたままアプリが非アクティブになっても閉じない。
NSMenu は必ず閉じるので、macOS の作法から外れている。
戻ってきたとき**打鍵が端末ではなくメニューへ入る**（a11y が「この周でやらないと嘘になる」と判定した項目）。

### 原因（判明している場合）

**OS のフォーカスが外れても DOM のフォーカスはメニュー項目に残る**ので、
周5-b PR 3 で入れた `focusout` では塞がらない（実機で Finder をアクティブにして確認）。

**`window` の `blur` を購読する形は採らなかった。関門を書けないため。**

| 試したこと | 結果 |
|---|---|
| E2E で `BrowserWindow.blur()`（Main 側から本物の経路） | **Renderer に `blur` が届かない** |
| その理由 | `BrowserWindow.isFocused()` が **最初から false**（`isVisible()` も false）。**一度も OS フォーカスを持たないので、外れようがない** |
| CDP で起動した実機 | `document.hasFocus()` が **false のまま**。`osascript` で前面に出そうとしたが **Apple Events の権限が無い**（-1743） |

⛔ **`dispatchEvent(new Event('blur'))` で済ませない。** それは自分で作った偽物なので、
**Chromium が本当に blur を投げるか**を1ミリも確かめない（恒真の関門になる）。

### 影響範囲

### 対処方針

      `/electron-ipc` を通す別の周にする。**Main 側なら E2E から `app.evaluate` で観測できる**
- [ ] 本物の `Cmd+Tab` での確認は**人力**（#195 の候補。Accessibility 権限か手操作が要る）

### 優先度

## 6. フォーカスに依存する検証は、エージェントが使える**どの環境でもできない**（周3 で確定）

### 症状

`BrowserWindow.getFocusedWindow()` / `isFocused()` / `window` の `blur` を見る経路は、
**E2E でも CDP 実機でも踏めない。** 4番（非アクティブ化で閉じない）と周3（#152）は
**同じ原因から出た別の面**で、4番は「blur が届かない」、周3 は「focus が誰にも無い」。

| 環境 | フォーカス | 理由 |
|---|---|---|
| `make e2e` | **原理的に持てない** | `harness.ts:571-589` が `BrowserWindow.prototype.focus` / `show` / `showInactive` / `moveTop` を **noop へ差し替え**、全ウィンドウを `hide()` し `dock.hide()` する |
| CDP 実機（`--remote-debugging-port`） | **持てない** | `document.hasFocus()` が false のまま。`osascript` で前に出そうとすると Apple Events の権限が無い（-1743） |
| 通常起動（人が使う状態） | **正しく動く** | 周3 で実測（`parent` 付き子ウィンドウが生成時にフォーカスを取り、`親.focus()` で親へ戻る） |

⛔ **ハーネスの非表示化は直さない。** 「開発者のエディタからフォーカスを奪わない」ための
意図的な設計で、外すと**テストの本数だけウィンドウが前に出る**。

### 影響範囲

- **フォーカスを見る判定は、純粋関数へ切り出して unit で固定するのが既定の作法になる**
  （`menu-action-routing.ts` が10例目）。**E2E に書くと恒真の関門になる**
- **実機の最終確認は必ず人力**（`#195` の A-6）。ネイティブメニューは DOM の外にあり、
  かつ `agent-browser` のマウス操作はページに DOM イベントを届けない（3番）
- ⚠ **周4（#153 = 設定ウィンドウの位置と高さの復元）に入る前に、確かめ方を計画で決めること。**
  設定ウィンドウは E2E では一度も `show()` されない。`getBounds()` 自体は隠れていても読めるが、
  **「復元された結果が画面でどう見えるか」は同じ壁の内側にある**

### 対処方針

- [x] 周3 で `limitations.md` に節として書いた（「OS のフォーカスに依存する判定は E2E から踏めない」）
- [ ] 4番（`win.on('blur')` を IPC で渡す）を周として起こすなら、**Main 側なら `app.evaluate` から
      観測できる**という 4番の見立てが正しいかを最初に実測する（この表の1行目は Renderer 側の話）

### 優先度

P2（作法として全周に効く）

### ステータス

## 12. 会話が0往復の gemini セッションは、gemini をもう1つ起動しただけで削除される

> ⛔ **2026-08-06 に全面訂正。** 初版は「`gemini --list-sessions` が走行中セッションを削除する」と
> 書いていたが、**誤り**。誤りの作り方は下の「なぜ間違えたか」に残す（同じ罠を踏まないため）。

### 症状

Gemini CLI は起動するたびに「中身の無いセッション」を掃除する。そのため、**gemini を起動して
一度も入力しないうちに別の gemini を起動する**と、**最初のセッションの JSONL が削除される**。

このアプリで踏む形:

- gemini タブを開いた直後に、**2つ目の gemini タブを開く**
- gemini タブを開いた直後に、**サイドバーの「履歴」で provider を gemini にする / 再読込を押す**
  （`src/main/history/reader.ts` が `gemini --list-sessions` を実行する = gemini の起動）

**一度でも会話していれば消えない。** 走行中でも `--list-sessions` に正しく出る。

### 実測（2026-08-06 / Gemini CLI 0.53.0）

| 条件 | `--list-sessions` に出るか | 他の gemini 起動で消えるか |
|---|---|---|
| 会話0往復（初期コンテキストのみ / 2行） | ❌ 出ない | ⚠ **消える** |
| 会話1往復以上（6行〜） | ✅ **出る**（走行中でも） | ✅ 消えない |

- 削除の主体は **`--list-sessions` ではなく gemini の起動全般**（`-p` の通常起動でも同じことが起きた）
- ⚠ **消されたあと会話を始めたらファイルが復活するかは未確認**。走行中プロセスは
  セッションファイルの fd を**保持していない**（`lsof` で確認）ので、次の書き込みで
  再作成される可能性は高い。**復活するならこの項目は「記録のみ」に降格できる**

### ⛔ なぜ間違えたか（**この項目で一番価値のある部分**）

初版は「**走行中**セッションが消える / 一覧に出ない」と書き、**2回再現した**と主張していた。
実際には**2回とも会話が成立しておらず、空セッションを測っていた**。

- `pty` 経由でテキストを書いても **Enter が届かない**（`\r` でも `\n` でも、write を分けても）。
  **入力欄に文字は乗る**ので、画面をダンプするまで気づけなかった
- 「2回再現した」は**同じ誤りを2回踏んだ**だけだった。**再現回数は正しさの根拠にならない**
- この誤りで **#155 を一度「実装しない」で close し、再オープンする手戻り**を出した

⭐ **教訓: 前提を作る操作そのものを検証する。** 「会話済みのセッションを作った」は
**作ったつもり**であって、`stat()` の行数（2行 -> 6行）を見れば即座に分かった。
**測定対象の状態を assert してから測る**（loop.md の「検査が意味を持つ条件を同じ spec の中で assert する」と同じ話）。

会話済みのセッションを確実に作るには **`gemini -i <prompt>`**（プロンプトを実行してから
対話モードに留まる）。手順は `.claude/skills/ai-cli/reference/cli-flags.md` が唯一の正。

### 影響範囲

- `src/main/history/reader.ts` の `listGeminiHistory()` は**破壊の主体ではない**が、
  gemini を起動する以上、掃除の引き金にはなる
- README のトラブルシューティングに利用者向けの回避策を書いた
  （「gemini タブを開いたら、まず1つ用件を送ってから次のタブを開く」）
- ⚠ **#155 の判断とは切り離すこと。** 会話済みセッションは走行中でも履歴に出るので、
  **#155 は実装可能**（一度これを混同して #155 を誤って閉じた）
- ⭐ **#155 の実装後、これが gemini で唯一残った「閉じると戻れない」経路になった**
  （2026-08-06 / PR #222・#223）。tmux セッション名は `aiterm-<採番した UUID>` で
  安定するが、**会話0往復のセッションは `--list-sessions` に出ないので選び直せない**。
  しかも `closeTabCopy` の分類は `agentSessionId` の有無で見るので、**この場合は
  「回収できる」側に入り、確認も出ない**（Renderer から往復数を知る手段が無い）。
  design-review で macOS / IA / 保守の3人が独立に指摘した。
