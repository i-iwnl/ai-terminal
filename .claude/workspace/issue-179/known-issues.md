## 4. #165 後半は「色を明るくする」では解けない（周2 の design-review で判明）

### 症状

プロバイダ色3本を高コントラストの面（`#525252`）で 3:1 に届かせる案（色相・彩度を保って明度だけ上げる）を
5ペルソナにレビューさせたところ、**5人中4人が独立に「その解き方は現状より悪化させる」と指摘した。**

案の色（shell `#9ea2aa` / claude `#d99179` / gemini `#71a8d1`）を実測すると:

| 測る対象 | 現状 | 案 | 向き |
|---|---|---|---|
| 面（`#525252`）との比 | 2.40 / 2.00 / 2.26 | 3.05 / 3.08 / 3.06 | **改善**（狙いどおり） |
| **フォーカスリング（白）との比** | 3.25 / 3.90 / 3.46 | **2.54 / 2.56 / 2.55** | **3:1 割れ** |
| **帯どうしの相互比** | 1.20 / 1.06 / 1.13 | **1.01 / 1.00 / 1.01** | **等輝度＝識別不能** |

### 原因

**3本を「面との 3:1 をぎりぎり超える最小値」に揃えると、必然的に等輝度になる。**
相対輝度が 0.3601 / 0.3612 / 0.3638（幅 0.0037）に収束し、ΔE76 が輝度成分を失う。
`design-rules.md` が却下事例に挙げた「位置が同じで色だけ違う」と**構造がまったく同じ**
（前回は左端3px、今回は上端2px。前回の却下理由「提案色は現状より悪化していた」も同じ）。

さらに a11y レビューが**両立不能を証明**した:

```
対 #525252 で 3:1 を満たすには  L >= 0.3531
対 #ffffff  で 3:1 を満たすには  L <= 0.3000
-> 区間が交わらない。24bit の全色に解が無い。
```

`.tab-bar__tab` の `border-top: 2px` の真下に、`outline-offset: -2px` のフォーカスリング（白2px）が
**隙間 0px で接する**。**輝度軸だけでは、面との 3:1 とリングとの 3:1 を同時に満たせない。**

### 影響範囲

- **#165 後半のスコープが変わる。** 「`@media` に3本足す」では終わらず、
  輝度以外の軸（**位置**または**形**）を使う設計が要る
  （例: 帯の水平位置をプロバイダごとに変える / 実線と破線を分ける。どちらも追加ピクセル0・新トークン0）
- あるいはフォーカスリングの `outline-offset` を `-4px` にして帯とリングの間に塗りを挟む（1セレクタ2行）

### 対処方針

- [x] 周2 で**関門だけ先に作った**（`S41` の `ADJACENT_HIGH_NOW`。フォーカスリングとの比と帯どうしの比を固定し、
      フォーカスリング側には 3:1 の閾値 assert を置いた）。**色を動かすと必ずここが赤くなる**
- [x] 周1 が `S41` に残した是正指示（「`high > normal` に切り替えよ」）が**誤りだった**ので訂正した。
      `providerTargets` は面自体が動くので、normal と high の大小比較に意味がない
- [ ] **#165 後半は周を1つ増やして扱う**（`overview.md` の周表を参照）。この周では色を決めない

### 優先度

P2

### ステータス

調査済み・関門は作成済み・**色の決定は未着手**

## 7. macOS の「コントラストを上げる」が実際に `@media` に到達するか、一度も観測されていない

> **2026-08-05: 解決。ユーザーが実機で確認し、「コントラストを上げる」で実際にタブバーの配色が変わった。**
> **OS 設定は `@media (prefers-contrast: more)` に到達している** = #134 / #165 / #179 で
> 高コントラスト側にかけた作業（トークン11本ぶん）は実際に効いている。
> 記録は `.claude/skills/e2e/reference/limitations.md` の「OS のシステム設定に依存する確認」。
> （いったん #195 の A-4 へ移したが、そこで消化された）

### 症状

`@media (prefers-contrast: more)` の分岐は S41 が固定しているが、**S41 が使うのは
Playwright の `emulateMedia({ contrast: 'more' })`** で、これは CSS の分岐が正しいことしか示さない。
**OS のシステム設定「コントラストを上げる」がその分岐に到達することは、一度も観測されていない。**

`README.md` は「追従する」と断言している。**ここが偽なら、#134 / #165 で高コントラスト側に
かけた作業（トークン11本ぶん）は誰にも届いていない。**

### 原因（判明している場合）

Electron / Chromium が macOS の `NSWorkaceAccessibilityDisplayShouldIncreaseContrast` を
`prefers-contrast` に反映するかどうかは、バージョン依存で変わりうる。
**agent-browser（CDP）も OS 設定には届かない**ので、エージェントでは検証できない。

### 影響範囲

- 高コントラスト側の実装すべて（`@media` の11トークン）

### 対処方針

- [ ] **人が実機で1度だけ確認する。** システム環境設定 > アクセシビリティ > ディスプレイ >
      「コントラストを上げる」を入れ、タブバーの色が変わるかを見る
- [ ] 結果を `.claude/skills/e2e/reference/limitations.md` に実施日つきで記録する
- [ ] **偽だった場合のみ** known-issues に書き戻す（真なら記録だけでよい）

### 優先度

P2（ただし**偽だった場合の影響は大きい**）

### ステータス

## 6. #165 後半の設計（周2.5 の design-review で確定した制約と、残りの手順）

### 確定した制約（3人が独立に実測・証明。**次の周はここから読む**）

1. **`dotted` は使えない。** Chromium の 2px 点線は「2px 塗り / 2px 空き」= **インク被覆 50%**。
   帯の空間平均輝度が落ちるので、**色を 3:1 まで上げても帯の実効比は 2.00 にしかならない**。
   点線のまま実効 3:1 を出すには L=0.622（`#cfcfcf` 相当）が要り、`--text-secondary` より明るくなる。
   **線種の案は、色を上げる案（R）を打ち消す。**
   `dashed` は 6px/3px（被覆 68〜73%）なので使えなくはないが、実効 3:1 に L=0.4797 が要る。
2. **太さ（2/3/4px）ならインク被覆 100% を保つ**ので R を打ち消さない。しかも `border-top-color` の
   ままなので `contrast.ts` の改修が要らず、`box-sizing: border-box` で外形高さも不変。
3. **識別軸は `@media (prefers-contrast: more)` の中だけに閉じる。** そうすれば既定は1px も動かず、
   `docs/images/` の撮り直しが **0枚**で済む。既定にも広げると **S09 / S19 の2枚**が必ず落ちる
   （claude / gemini タブが写る画像はこの2枚だけ）。
4. **P（`outline-offset: -4px`）には下辺の副作用がある。** `.tab-bar__tab.is-active` の
   `box-shadow: inset 0 -2px 0 var(--focus-ring)` とリング下辺が接し、
   **選択中かつフォーカス中の下辺が白 4px の塊になる**。`styles.css` は「4辺白のリングと区別するため
   選択は下辺 2px に留める（面積差で区別する）」と理由を明示しているので、
   **承知して受けるなら CSS コメントと spec に書き残す**こと。
   （なお下辺2px は現状リングと完全に重なっており、「面積差で区別」は下辺については元々成立していない）
5. **`ADJACENT_HIGH_NOW` の「帯どうし」は、厳密には隣接していない。** タブ間には
   `border-right: 1px solid var(--border-subtle)`（高コントラストで `#7a7a7a`）が挟まる。
   **隣接比の問題ではなく「絶対同定」の問題**として扱う（結論は変わらないが根拠の置き場が違う）。
6. **線種・太さを入れても「プロバイダ名が常時不可視」は1ミリも改善しない。** 形が与えるのは
   *弁別*（隣り合う2枚が別物と分かる）であって *同定*（どれが Claude か）ではない。
   凡例が画面に無く、**タブが1枚のときは情報量ゼロ**。`known-issues` に「解決した」と書かないこと。

### 残りの手順（この順で。**PR 1 = #186 は完了済み**）

| PR | 内容 | 値の変更 | 画像 |
|---|---|---|---|
| ~~1~~ | ~~`css-tokens.test.ts` の `splitRoot` が `@media` 内を素通りする穴~~ **完了（#186）** | なし | 0枚 |
| 2 | **P（`outline-offset: -4px`）+ 幾何の関門** | なし | 0枚 |
| 3 | **識別軸（太さ）+ R（色を 3:1 へ）を同時に、`@media` の中だけで** | あり | 0枚 |

### PR 2 の作り方（3人が具体的に指定した）

**⛔ `expect(getComputedStyle(btn).outlineOffset).toBe('-4px')` と書かない。**
CSS の宣言を言い換えただけで、`contrast.ts` 冒頭が「宣言値ではなく解決された実効値を見る」と
言って捨てた形と同型。

- 置き場は `src/renderer/src/tabs/tabBandGeometry.ts`（純粋関数。前例が8つある作法）。
  `tabs/` に4本の前例があり、PTY も IPC も跨がないので `src/shared/` には置かない
- API: `providerBand(borderTopWidth)` / `focusRingBand(borderTopWidth, outlineWidth, outlineOffset)` /
  `gapPx(a, b)`。**offset の符号とリングが内外どちらに伸びるかは間違えやすい**ので、
  そこを純粋関数に閉じて unit で固定することに価値がある
- `test/unit/tab-band-geometry.test.ts` で characterization: `offset -2 -> gap 0`、`-4 -> gap 2`。
  **現状の 0 も一緒に固定する**（S40 と同じ作法）
- E2E は S51 の手順（`.tab-bar__new` を focus -> `Shift+Tab`）で**本物の `:focus-visible`** を作り、
  (a) `buttonRect.top - tabRect.top === borderTopWidth`（`align-self: stretch` の前提を実測で検算）
  (b) computed の3値を純粋関数へ流して `gapPx >= 2`
- **`ADJACENT_HIGH_NOW` のフォーカスリング 3:1 assert を gap に条件づける。**
  `gap === 0` のときだけ 3:1 を要求し、`gap > 0` なら外す。**逆向きの番人**（`staleFail` と同じ形）で
  「gap が 0 に戻ったのに 3:1 が外れたまま」「gap > 0 なのに 3:1 が残っている」を落とす。
  これが無いと P は**理由を誰も知らない `-4px`** になり、次のリファクタで静かに消える
- S78 に「選択中 × フォーカス時の下辺」を固定する項目を足す（制約4）
- **実機確認が必須**: フォーカス中のアクティブタブは E2E も撮影レーンも作らない。
  リング右端と閉じるボタン `x` の距離が **3px -> 1px** に縮む（実測）ので、目で見る

## 9. `zsh` の終了コードは直前のコマンドの終了ステータスなので、赤が誤爆する（周3 の design-review で発見）

### 症状

周3 で「異常終了だけ赤」にしたが、**`zsh` に `exit` と打ったときの終了コードは
直前に実行したコマンドの終了ステータス**になる。実測（2026-08-05）:

```
zsh -ic 'grep -q zzz_no_such /etc/hosts; exit'   -> 1
zsh -c  'true; exit'                              -> 0
```

つまり **`grep` や `test` や `rg` を空振りした直後に `exit`（または Ctrl+D）した
shell タブが「異常終了」として赤くなる。**

### 原因（判明している場合）

`isAbnormalExit()`（`src/shared/pty-exit.ts`）は `exitCode !== 0` を見るだけで、
**その PTY が shell か AI CLI かを区別していない**（呼び出し側が `ptyKind` を渡していない）。

**今日すでに同じ誤爆が起きている**: `shouldBounceOnExit` が同じ判定を使うので、
`grep` 空振り後に `exit` してウィンドウを裏に回すと Dock が跳ねる。

### 影響範囲

- **#166 が直そうとした問題（赤が信用されなくなる）の再生産になりうる。**
  ヘビーユーザーのレビューでは「shell タブの終了の半分近くが 1 で返る」と見積もられた
- ただし**着手前は全部の終了が赤かった**ので、誤爆を含めても**厳密には改善**している
  （正常終了した shell タブの多数派は赤くなくなった）

### 対処方針

- [ ] 案 (a): `ptyKind === 'shell'` は severity を出さない（エージェントの異常終了だけ赤にする）。
      このアプリの存在理由（エージェントを飼う）と一致するので、レビュアーはこちらを推した
- [ ] 案 (b): そのまま出し、偽陽性を受け入れる
- **周3 では判定を変えなかった。** #166 本文が「`severityForExit()` / `isAbnormalExit()` を
  使い回す。**新しい判定を書かない**」と明示指定していたため。切り出すなら #179 の周を1つ増やす

### 優先度

P2

### ステータス

**2026-08-05: [#195](https://github.com/i-iwnl/ai-terminal/issues/195) の B-1 に移した。** (a) / (b) の選択は
製品の意思決定なので人が決める。**決まればエージェントが実装する**（実装自体は小さい）。
