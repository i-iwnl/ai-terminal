## 4. README の S22 の画像に、変換中の文字列が写っていない

> **GitHub Issue**: [#10](https://github.com/Yoshinaga-iwnl/ai-terminal/issues/10)
### 症状

`docs/images/S22-ime-composition.png` は「変換中（未確定）の文字列がその場に表示」というキャプション付きで枠を強調しているが、**枠の中が空**で肝心の「にほんご」が写っていない。画像だけを見ると、何も起きていないように見える。

### 原因

未調査。E2E の S22 は `expect(composition).toContainText('にほんご')` を通っているので、**DOM には存在している**。撮影時点の合成に反映されていないと思われる。

ウィンドウ非表示化の調査中に見つけたが、**非表示にする前に撮った画像（コミット済み）でも同じ**なので、この件は非表示化とは無関係の既存の問題。

### 影響範囲

- README の使い方ガイドの画像1枚のみ。アプリの動作には影響しない
- ただし「IME が動く」ことを示すための画像がそれを示せていないので、掲載価値が無い

### 対処方針

- [ ] `composition-view` の描画タイミングを調べ、撮影前に待つ条件を足す
- [ ] 直らなければ、その画像は README から外す（示せていない画像を載せない）

### 優先度

P2

### ステータス

**対処済み（2026-07-28）。** 原因は撮影ハーネス側だった。`annotateAndShoot()` が撮影直前に
`.xterm-helper-textarea` へ `visibility: hidden` を当てており、**visibility: hidden の要素は
フォーカスを保持できないためブラウザが非同期に blur する**。IME の入力を受けている要素が
blur されると composition が終了し、`.composition-view` から変換中の文字列が消えていた。
実測では hide 直後はまだ残っており、数百ミリ秒後に `display: none` になる。
`opacity: 0` に変えてフォーカスを保ったまま隠す形にし、撮影後に composition が生きていることを
spec の後置条件として検査するようにした（画像の中身は機械で見られないため）。

## 6. メモの自動保存が、アプリ終了時に取りこぼす可能性がある

> **GitHub Issue**: [#12](https://github.com/Yoshinaga-iwnl/ai-terminal/issues/12)
### 症状

メモは入力停止から 800ms 後に保存される。**それより早くアプリを終了した場合に保存されるかを検証していない。**

サイドバーのタブ切り替えでは blur が発火して即時保存されることを S29 で確認済みだが、ウィンドウを閉じる / アプリを終了する経路は確認していない。

### 原因

未調査。`MemoPanel` のアンマウント時には保留中のタイマーを解除しているだけで、フラッシュしていない。

### 影響範囲

- 直前に書いたメモが失われうる（最大 800ms 分の入力）
- 走り書きを保存する機能なので、失われると用途そのものが崩れる

### 対処方針

- [ ] アプリ終了 / ウィンドウクローズ時に保留中の保存がフラッシュされるかを確認する
- [ ] されないなら、アンマウント時に保留分を保存する（タイマー解除の前に flush する）

### 優先度

P2

### ステータス

**対処済み（2026-07-28）。「可能性がある」ではなく、実際に取りこぼしていた。**
先に回帰テスト S33 を書いて再現を確認した（`memos.json` が一切作られない）。
`MemoPanel` に保留中の内容を持つ `pendingRef` を足し、アンマウント時に解除ではなく
書き出すようにしたうえで、**`beforeunload` でも書き出す**。ウィンドウを閉じる経路では
React のアンマウントが走らないため、アンマウント時の flush だけでは足りなかった。

## 8. Electron の起動が、稀にウィンドウを出さないまま失敗する

> **GitHub Issue**: [#17](https://github.com/Yoshinaga-iwnl/ai-terminal/issues/17)

### 症状

`make e2e` のフル実行で、ほぼ毎回1件だけ flaky が出る。落ち方は必ず
`electronApplication.firstWindow: Timeout ... while waiting for event "window"`。
リトライで緑になる。

**特定のシナリオに寄らない。** 観測した範囲では S11 / S12 / S13 / S14 と毎回別の spec で起きており、

### 分かっていること

フル実行3回・99起動で `firstWindow` の所要時間を計測した。

| | 値 |
|---|---|
| 成功時 | 最小 101ms / 中央 119ms / 最大 421ms |

- `make e2e` の実行結果に恒常的に flaky が1件並ぶ。**本物の不安定さを見落とす土壌になる**
- リトライで吸収できているため、テストの信頼性そのものは今のところ落ちていない

### 対処方針

- [ ] 連続起動の副作用かを切り分ける（起動間隔を空ける / 1プロセスあたりの起動数を変える）
- [ ] Electron 側の既知の不具合が無いか調べる
- [ ] 切り分かなければ、flaky を「1件までは既知」として扱う根拠をこのファイルに残したうえで受け入れる

### ステータス

## 10. 「タスク一覧を現在のディレクトリに絞り込む」が一度も効いていなかった

> Issue 未起票（ユーザーからの直接報告。2026-07-29 に対処済み）

### 症状

`config.scopeAgentsToCwd` を true にしても、タスク一覧が絞り込まれない。設定パネルのチェックボックスは動き、`config.json` にも保存されるのに、一覧は変わらない。

### 原因

`src/renderer/src/sidebar/TaskList.tsx` が `window.api.agents.list({})` と**空の引数**で呼んでいた。Main 側（`poller.ts`）の絞り込み対象 `lastKnownCwd` はこの引数からしか更新されないため、永久に `undefined` のままだった。結果として `fetchTasks()` は設定に関わらず常に `listClaudeAgents(undefined)` を呼び、`--cwd` が一度も付かなかった。

`cwd?: string` は optional なので、`{}` を渡しても型エラーにならない。**「渡さない」と「渡し忘れ」が型の上で区別できない。**

### 影響範囲

- 実装当初からこの設定は機能していない（設定パネルで露出させた #5 以降、目に見える形で壊れていた）
- 複数プロジェクトを並行して回しているとき、一覧が絞れず用途が成立しない

### 対処

- [x] `TaskList.tsx` から `getSharedCwd()` を渡す（解決が非同期なので `subscribeSharedCwd` で伝え直す）
- [x] `poller.ts` の `lastKnownCwd` 初期値を Main の `process.cwd()` にする（初回ポーリングのちらつき防止）
- [x] 偽 CLI に `--cwd` の解釈を実装する（素通りしていたため、壊れていてもテストが緑になる状態だった）
- [x] S34（起動時）/ S35（設定パネルからの切り替え・往復）を追加

### 残っている注意

`TaskList` と `poller` の修正は**どちらか一方だけでも動く**（片方ずつ戻して確認済み）。S34 は両方戻したときしか赤くならないため、**将来どちらかが「使われていないコード」に見えて消される**危険がある。理由は `/ai-cli` の `reference/cli-flags.md` に記載した。

### 優先度

P1

### ステータス

対処済み（残タスクなし。Issue には起こしていない）
