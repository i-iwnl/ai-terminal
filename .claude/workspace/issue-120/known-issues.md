## 1. タブ幅 90px のうち 34px（38%）が、押しても何も起きない死角

### 症状

タブのどこを押しても選択される、という当然の期待が成り立っていない。
**タブ選択に有効なのは 90px 中 32px + タイトル領域だけ**で、左 25px と右 13px は
`.tab-bar__tab`（`<div>`。クリックハンドラを持たない）に当たって何も起きない。

周3 の実測（2枚目のタブ・hover 中、タブは x 350–440 の 90x35）。
`document.elementFromPoint` を y = タブ垂直中心で 1px 刻みに振った地図:

```
350–370  .tab-bar__tab        死角 21px（padding-left 12 + state-slot 6 + gap の左 3）
371–394  .tab-bar__close      当たり判定 24px
395–397  .tab-bar__tab-button 3px
398–426  .tab-bar__title      29px（tab-button の子）
427–439  .tab-bar__tab        死角 13px（padding-right 12 + border-right 1）
```

Safari / Terminal.app / VS Code はいずれもタブのどこを押しても選択される。

### 原因

`.tab-bar__tab` が `padding: 0 var(--sp-3)` を持つ flex コンテナで、
選択用の `.tab-bar__tab-button` は **その padding の内側で `flex: 1`** している。
padding と、先頭の `.tab-bar__state-slot`（6px。`pointer-events: none` の装飾）と
その後ろの `gap`（8px）は、どれも `.tab-bar__tab-button` の外側にある。

**PR #108（S69）は「タブの中央」の死角を直したもので、端の死角は対象外だった。**
S69 も中央 1点しか見ていないため、この帯は関門をすり抜けている。

### 影響範囲

- `src/renderer/src/tabs/TabBar.tsx`（DOM 構造）と `src/renderer/src/styles.css` の
  `.tab-bar__tab` / `.tab-bar__tab-button`
- `e2e/specs/S69-tab-select-center.spec.ts`（中央 1点 -> 帯で見る形への拡張）
- `e2e/specs/S44-target-size.spec.ts`、`S58-drop-target-highlight.spec.ts`
  （タブの D&D）、タブのダブルクリック改名・コンテキストメニュー

### 対処方針（未着手）

**周3 のスコープには入れなかった**（ユーザー判断。B-2 は CSS 数行で閉じるが、
こちらは TabBar.tsx の構造変更になり、D&D・改名・コンテキストメニューへの
波及確認が要るため）。

**B-2 と噛み合っている点に注意。** 周3 の B-2 は閉じるボタンの当たり判定を
左へ 10px 伸ばしており、その 10px は「いま死角である」ことを前提に無害と判断した。
**タブ全体をクリック対象にすると、その 10px は生きた選択領域に変わる。**
両方を直すときは、閉じるボタンの左のはみ出しが
「タブ選択を狙って外す位置ではない」（state-slot と gap の上で、タイトルからは遠い）
ことを改めて確認すること。design-rules.md
「入れ子の破壊的ターゲットは、隣のターゲットへ向かう向きにだけは見た目を越えない」の適用。

**新しい Issue は起票しない**（このセッションの方針: 既存 Issue を溶かしきることに集中する）。
周6 か #121（P3）で扱う。

## 2. S69 が一度だけ flaky になり、原因を特定できなかった

### 症状

周4 の検証バッチ（S61 / S63 / S57 / S60 / S56 / S42 / S25 / S07 / S44 / S69）で
**S69 が1回だけ flaky**（retry で green）。バッチ全体の所要は 29.1s。

### 分かっていること

- **再現しない。** `--repeat-each=8 --retries=0` で 8/8 green。
  同じバッチを回し直すと 10 passed（flaky 0）で**所要 8.5s**（3.4倍速い）
- 発生したのは **C-1 の負荷検証で Electron を 360 回起動した直後**
  （CPU を 16 本のビジーループで埋めた状態を長時間維持したあと）
- **エラー内容を取り損ねた**（`test-results/` を消してから気づいた）

### 評価

所要時間が 3.4 倍だったことから**マシン負荷が最有力**。
起動 flake（`firstWindow: Timeout` = #121 の B-3）であれば既知だが、
**証拠が無いので断定しない。**

周3 の CSS 変更が原因である可能性は低い。S69 はタブ中央（1枚目のタブなら x≈305）を
押すが、**周3 の変更はむしろ余裕を増やしている**:

| | 閉じるボタンの当たり判定 | S69 のクリック位置との距離 |
|---|---|---|
| 変更前 | x 281–305（要素 286–300 の中央に 24px） | **0px（ちょうど右端に接していた）** |
| 変更後 | x 276–300 | 5px |

### 結論（周6 のフル実行で確認済み）

**再発しなかった。マシン負荷として閉じる。**

周6 の `make e2e` フル実行（94 起動 = spec 81 + 撮影 13）で **S69 は1度も落ちなかった**
（ログ中の出現 0 回）。同じ実行で出た flaky 6件は**すべて `firstWindow: Timeout`**
（= #17 / #121 の B-3 の起動 flake）で、S69 とは別物。

**この項目はこれ以上追わない。**

## 3. 撮影レーンに残る非決定性は「セッション UUID」だけになった

### 現状

周5 で、同じコードで連続2回撮って**画素差ゼロの枚数が 0/13 -> 11/13** になった。

| 消したもの | 手当て |
|---|---|
| タスク行の経過時間（**撮るたび**に増える） | `agents.json` の `startedAt` を `Date.now() - 固定オフセット` に |
| 履歴行の `N日前`（**1日に1回**増える） | 履歴 JSONL の mtime を同様に相対化 |
| S01 がサイドバー空状態で撮れることがある | サイドバーが写る6画面に `waitForTaskList()` |

**残っているのは S09 と S56 の2枚だけ**で、原因は**セッション UUID**。
アプリが `--session-id` に渡す UUID を `randomUUID()` で採番するため、
ターミナルに出る `ARGS: --session-id <uuid>` の行が毎回変わる。

### 対処方針（未着手）

ハーネスからは手が出せない（アプリ側が採番する）。選択肢:

- 環境変数で UUID を固定できる口をアプリに開ける（**製品コードをテスト都合で変える**）
- 撮影時だけその行を隠す（`annotateAndShoot` の既存の「一時的に隠す」手法と同型）
- 許容する（2枚だけなら、撮り直しのたびに目視で確認できる）

**#121 の B-2「生成画像と差分ゼロを検査する」は、この2枚が残る限り
そのままでは成立しない**（11枚だけを対象にするか、しきい値付き比較にする必要がある）。
`issue-119/known-issues.md` の 8 のうち、**経過時間の分と注釈の配置の反転は解消**、
**セッション UUID と起動 flake が残っている**。

**新しい Issue は起票しない**（このセッションの方針）。#121（P3）の B-2 で扱う。

## 4. E-1（Webhook URL を safeStorage へ）— 着手条件は今も満たされていない

### 判断

**実装しない。周知で足りているという判断は今も有効。** 周6 で前提を4点とも実コードで確認した。

| 前提 | 確認結果 |
|---|---|
| `safeStorage` は未実装 | `grep -rn "safeStorage" src/` が **0件** |
| README に明記されている | `README.md`「**Webhook URL は `config.json` に平文で保存される。** リポジトリに含まれる場所ではないが、設定ファイルを共有・バックアップするときは注意すること」 |
| 設定パネルに明記されている | `SettingsPanel.tsx` の「Slack / Discord への転送」節に「URL は config.json に平文で保存されます」 |
| **着手条件（設定ファイルを共有・同期する運用）が始まっていない** | 設定の**エクスポート・インポート・同期・バックアップの機能が1つも無い**（`config.ts` / `settings/` に該当コードなし）。config.json は手で触るしかなく、その場で README と設定パネルの両方が警告している |

### 実装する判断に変わったときの必須条件（先に書き残す）

**`safeStorage` だけを入れてはいけない。** 次の3つをセットで作ること。

1. **既存の平文からの移行経路。** 既に URL を入れている利用者の設定が、
   アップデートで黙って空になってはいけない
2. **復号できなかったときに、送信が黙って止まらないこと。** `safeStorage` は
   Keychain に依存するので、別マシンへ config を持ち込む・キーチェーンが
   ロックされている等で読めなくなる。**そのとき通知バナーで伝える**
   （このアプリの既定方針「何も起きないで終わらせない」。#120 C-2 と同じ型）
3. **`safeStorage.isEncryptionAvailable()` が false の環境での縮退。**
   平文にフォールバックするなら、そのことを画面に出す

### なぜ今やらないか

**秘匿の必要が生じていないのに暗号化を足すと、上の3つの failure mode を
新しく抱え込むだけになる。** 特に 2 は「通知が届かなくなったが理由が分からない」
という、いま存在しない不具合を作る。周知は README と設定パネルの2箇所で
届いており、config.json を共有する動線がアプリ側に無い。

**新しい Issue は起票しない。** 着手条件が満たされた時点で、この節を根拠に起票する。

## 5. 起動 flake の発生率が、記録より高く出た

### 観測（周6 の `make e2e` フル実行）

**94 起動中 6 件**（6.4%）が `electronApplication.firstWindow: Timeout`。
`retries: 1` で全部 green になったので実行結果は通っている。

内訳: S12（spec）/ S41 / S44 / S70 / S80 / S12（撮影）。
**特定のシナリオに寄っていない**という #17 の記述どおりの分布で、
**周5 で変更した S12 が spec と撮影の両方に出ているが、どちらもエラーは
`firstWindow: Timeout` で、周5 の変更とは無関係。**

### 記録との差

`#121` の B-3 に載っている実測は **99 起動中 2 回（2.0%）**。今回は 6.4% で **3倍以上**。

**このセッションでマシンを酷使している**（C-1 の対照実験で CPU を 16 本の
ビジーループで埋めたまま Electron を 360 回起動した）ので、その影響が
残っている可能性が高い。ただし**負荷生成プロセスは停止済み**で、
このフル実行の時点では他に重い処理を回していない。

### 対処方針（#121 B-3 で扱う）

**発生率の記録を更新する材料として使うこと。** B-3 は
「連続起動の副作用かを切り分ける（起動間隔を空ける / 1プロセスあたりの
起動数を変える）」を挙げているが、**撮影レーンが `make e2e` に入って
1回のフル実行あたりの起動数が 81 -> 94 に増えた**（周5 の D-1）ので、
その前後で率が変わるかも見られる。

**新しい Issue は起票しない。** #121 の B-3 に統合する。

## 6. `ownedByApp` の肯定側が検証できるようになった（未実装）

### これまで「原理的に不可能」だった理由

`.claude/skills/e2e/reference/limitations.md` は、`ownedByApp` が true になる側を
「偽 CLI の固定データにアプリが採番する UUID を含められないので**原理的に再現できない**」
として対象外に挙げていた。S15 は否定側（無関係な固定タスクが誤って owned にならないこと）
だけを見ている。

### 周5 の D-2 で前提が変わった

`setAgentEntries()` で `agents.json` を実行中に差し替えられるようになった。
そして**偽 claude はターミナルに `ARGS: --session-id <uuid>` を出す**
（`docs/images/S09-launch-claude.png` に写っている通り）。

つまり spec は次の順で肯定側を作れる。

1. `Cmd+Shift+C` などで claude タブを起動する
2. `.xterm-screen` から `--session-id` の UUID を読み取る
3. その sessionId を持つエントリを `setAgentEntries()` で書き込む
4. `.task-item--owned` が1件になり、行がクリック可能になることを見る

**S15 の対象範囲がそのまま広がる。** ついでに `S47`（タスク行のキーボード到達）が
固定 UUID `aaaaaaaa-…` を owned と決め打ちしている箇所も、実物に置き換えられる。

### 対処方針

**周6 のスコープには入れない**（周6 は D-3 の手動確認と E-1 の判断、締めの `make e2e`）。
**新しい Issue は起票しない。** #121（P3）で扱う。

`limitations.md` の該当行は「解消した。未実装」へ書き換え済み。
