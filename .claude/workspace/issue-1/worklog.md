## 2026-07-27 - E2E 方針の合意と Playwright 導入

### 実施内容

- Playwright の Electron 起動 API が使えることを確認（`@playwright/test@1.62.0`、`_electron.launch` が存在）
- アプリのエントリが `out/main/index.js` でビルド済みのため、そのまま駆動できることを確認
- 21シナリオ（S01-S21）を定義し、ユーザー承認を取得
- 隔離ハーネスの方式・シナリオ管理方式・CI 方針を決定
- `@playwright/test` を devDependency に追加（**未コミット**）

### 設計判断

- **隔離ハーネス方式（一時 HOME + PATH 先頭の偽 CLI）を採用**: このアプリは実 OS に触るため、素直に書くと (1) 実行のたびに結果が変わる（別ターミナルで claude を動かしていると一覧が変化する）、(2) **スクリーンショットに実プロジェクト名や実プロンプトが写り込む**。後者は README に載せる画像としては事故になる。アプリ本体にテスト用の分岐を入れる案もあったが、本番コードにテスト専用コードを残さない方を選んだ
- **偽 CLI は受け取った引数を出力する設計にする**: これにより `--session-id` や `--resume` が正しく渡ったかまで検証できる。単に固定出力を返すだけだと「アプリが CLI をどう呼んだか」が検証できない
- **シナリオ管理はレジストリ + lint**: `e2e/scenarios.yml` を唯一の正とし、`scripts/lint-e2e.mjs` で spec との 1:1 を機械検査する。`.claude/scripts/lint-skills.sh` と同じ「規約を文章ではなく機械に守らせる」思想
- **スクリーンショットの注釈は DOM オーバーレイ注入で行う**: 撮影直前に番号バッジ・矢印・日本語キャプションを DOM に差し込んでから撮る。画像処理ライブラリを追加せずに済み、文言の修正がコードの1行変更で済む
- **CI には載せない（ローカル実行のみ）**: Electron の GUI テストは Linux ランナーで xvfb が必要になり、macOS ランナーは高価。既存 CI（typecheck / lint / build）は軽いまま保つ

### 教訓

- **DevTools を開かないと見えない不具合がある。** preload の読み込み失敗は Renderer のコンソールにしか出ず、ターミナル側には一切出力されない。「ウィンドウが開いた＝起動成功」という確認は不十分だった。E2E で最初に潰すべきはここ（S01/S02 がこれに対応する）
- node-pty の `spawn-helper` は npm install で実行権限が落ちることがあり、`posix_spawnp failed` という原因の分かりにくいエラーになる。`postinstall` で復元しているが、**CI やコンテナで環境を作り直すたびに再発しうる**ので、E2E の実行前提として意識しておく

### 次に再開するとき最初に読むべきこと

1. `git status` — `package.json` と `package-lock.json` に `@playwright/test` の追加が**未コミットで残っている**はず。ここから再開する
2. `overview.md` の「4. 直近の次アクション」— P0 は隔離ハーネスと `e2e/scenarios.yml`。**この2つは全 spec が依存する共通基盤なので、並列化せず先に確定させること**
3. Issue #1 の本文にシナリオ21件の完全な定義がある。`e2e/scenarios.yml` はここから起こす
4. `known-issues.md` の「1. Phase 1 の受け入れ基準が未検証」— E2E とは別に、日本語 IME など手動確認が残っている

## 2026-07-27 - E2E 基盤の実装完了と、それが見つけたアプリのバグ

### 実施内容

- 隔離ハーネス（一時 HOME + PATH 先頭の偽 CLI + JSONL フィクスチャ）を実装
- `e2e/scenarios.yml` をシナリオの唯一の正として確定。`scripts/lint-e2e.mjs` で spec との 1:1 を機械検査
- **S01 から S22 まで全22 spec が green**（当初21件 + IME の S22 を追加）
- スクリーンショット11枚を撮影し、README に画像付きの使い方ガイドを追加
- `.claude/skills/e2e/` として運用を skill 化

### 設計判断

- **IME はテストできると判明したので S22 を追加した。** 当初「OS レベルの入力なので自動化不能」と判断していたが、Chromium の DevTools Protocol に `Input.imeSetComposition` があり、Electron 経由で叩ける。変換中の文字列が `.composition-view` に出るところまで検証できる。ただし macOS の入力メソッドとの実際の相互作用は再現していないので、手動チェックリストは残す
- **`--disable-gpu` で Electron を起動する。** そうしないと xterm が WebGL レンダラになり、文字が canvas に描かれて DOM から読めない。GPU を無効にするとアプリの try/catch が DOM レンダラにフォールバックし、テキストを検証できるようになる。副次的に「WebGL が使えない環境でも動く」ことの検証にもなっている
- **偽 CLI は受け取った引数を出力する。** これにより `--session-id` や `--resume` が正しく渡ったかを画面から検証できる

### 教訓

- **E2E がアプリの実バグを1件見つけた。** タブを開いた直後の PTY 出力が、Renderer が購読を始める前に届いて失われていた。AI CLI の起動バナーが消え、ターミナルが空のまま何も起きないように見える。`src/renderer/src/terminal/ptyStream.ts` を新設し、購読者がいない ptyId の出力をバッファして購読開始時にフラッシュする形で修正。修正後、実行時間が 49 秒から 17 秒に短縮された（競合による待ちが消えたため）
- **壊れた JSONL で `parseError` が付いていなかった**（全行がパース不能でも例外が出ないため）。壊れたセッションが「中身の無い正常なセッション」と区別できない状態だった。設計方針（壊れたエントリを隠さない）に反するので `src/main/history/reader.ts` を修正
- **フィクスチャを推測で書くと、間違った形を検証してしまう。** `ai-title` 行のキーを `title` と書いたが、実データ330ファイルを走査したところ正解は `aiTitle` だった。アプリの実装が正しく、フィクスチャが誤っていた。**外部フォーマットのフィクスチャは、書く前に実データを走査して確認すること**
- **macOS の一時ディレクトリは `/var` 配下だが `/var` は `/private/var` へのシンボリックリンク。** OS の `getcwd()` は正規化した側を返すため、`realpathSync` を取らないとアプリの探すパスとずれる
- **Electron の userData は HOME の差し替えを無視する。** `--user-data-dir` を分けないとテスト間で状態が混ざる
- **スクリーンショットは撮って終わりにしない。** 「コマンドを打てば結果が返る」と説明した画像に出力行が写っていない、注釈が対象の文字を覆っている、といった食い違いが3枚あった。1枚ずつ目で見て、キャプションの主張が画像から確認できるかを検証する必要がある
- シェルのプロンプトを固定しないと、実マシンのユーザー名とホスト名がスクリーンショットに写り込む

### 次に再開するとき最初に読むべきこと

1. **Issue #1 の完了条件はすべて満たしている。** 検証結果: `make check` green / E2E 22件 green / `lint-e2e` PASS=166 FAIL=0 WARN=0 / `lint-skills` PASS=66 FAIL=0
2. 残っているのは**コミットと PR**。ブランチは `feat/e2e-playwright`（`feat/workspace-context-management` の上に積んでいる。PR #2 がマージされたらリベースが必要）
3. **未着手のまま残っている P0 が別にある**: `known-issues.md` の「1. Phase 1 の受け入れ基準が未検証」。E2E で自動化できた範囲は増えたが、vim / htop の描画品質と macOS の実 IME は人が触るしかない
4. アプリ側のバグ修正が2件入っている（`ptyStream.ts` の新設、`reader.ts` の `parseError`）。E2E のコミットとは性質が違うので、コミットを分けること

## 2026-07-28 - `make dev` でターミナルが真っ黒になる不具合の原因特定と修正

### 実施内容

- 「キーボードで入力ができない」という報告を調査。**症状の実体は入力ではなく描画**だった
- 原因: `@xterm/xterm/css/xterm.css` がどこからも import されていなかった。`src/renderer/src/main.tsx` に追加して修正
- 切り分けのため使い捨ての Playwright probe を書き、GPU 有効 / 無効の2条件で比較した（調査後に削除）

  | 条件 | レンダラ | 入力の PTY 到達 | 画面表示 |
  |---|---|---|---|
  | `--disable-gpu` あり（= E2E） | DOM | 到達する | 正常 |
  | `--disable-gpu` なし（= `make dev`） | WebGL | **到達する** | **真っ黒（何も出ない）** |

- 修正後、WebGL レンダラでもプロンプト・入力・出力すべてが描画されることをスクリーンショットで確認
- 検証: `make check` green / E2E 22件 green

### 設計判断

- **「入力できない」という報告を、入力の問題として調べない。** PTY への到達は画面を見ずに判定できる（シェルに `echo > ファイル` を実行させ、ファイルの有無を見る）。この判定を最初に入れたことで「入力は届いている＝描画の問題」と即座に確定でき、入力経路（`term.onData` -> IPC -> `pty.write`）の調査を打ち切れた
- **仮説は必ず実験で潰す。** 最初に立てた仮説は「StrictMode の二重 mount」だったが、開発ビルドで観測したところ `.xterm` は1個で入力も正常だった。**実験していなければ、この誤った原因で修正を書いていた**
- **`WebglAddon` の読み込み順（`term.open()` の後）も揃えたが、これは今回の原因ではない。** 順序を戻しても CSS さえあれば正常に描画されることを確認済み。xterm.js のドキュメント通りの形にする意味しかないので、不要と判断すれば落としてよい

### 教訓

- **E2E 22件が全て green でも、ユーザーが使う経路が壊れていることがある。** ハーネスが `--disable-gpu` 固定なので、E2E は DOM レンダラしか通らない。DOM レンダラは文字を実 DOM のテキストノードとして描くため、**xterm.css が無くても表示されてしまう**。この不具合は E2E の構造上、原理的に検出できなかった（`known-issues.md` の 5 番に記録）
- **テスト容易性のための設定が、そのまま検証の盲点になる。** `--disable-gpu` は「canvas だと DOM から文字が読めない」という正当な理由で入れたもので、判断自体は間違っていない。間違っていたのは、**その裏返しとして何が検証されなくなるかを書き残さなかったこと**
- **ライブラリ付属の CSS の import 漏れは、型チェックにも Lint にも E2E にも引っかからない。** どの静的ゲートも通り抜ける種類の欠陥がある

### 次に再開するとき最初に読むべきこと

1. 修正は2ファイル: `src/renderer/src/main.tsx`（xterm.css の import = 本命の修正）と `src/renderer/src/terminal/useTerminal.ts`（WebglAddon の読み込み順。**原因ではない**）。**いずれも未コミット**
2. **未対応の再発防止策がある**: `known-issues.md` の 5 番。GPU 有効で canvas を撮って非空を判定するシナリオを1件追加する。これを入れないと同じ種類の不具合をまた見逃す
3. `CLAUDE.md` の未コミット1行（`/e2e` の導線）も残ったまま。`origin/main`（`fe862f3`）へのリベースも未実施
4. Phase 1 の手動検証（`known-issues.md` の 1 番）は依然 P0 で未対処。今回 `make dev` が実用状態に戻ったので、ようやく実施できる
