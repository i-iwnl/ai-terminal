## 3. 選択中タブの「終了」テキストが、既定の配色で 4.5:1 を割ったまま残っている

> **出典**: Issue #134 の design-review（2026-08-04、#160 の周3）

### 症状

`.tab-bar__tab.is-active.is-exited` の文字色と `.tab-bar__exit-badge` が、
`--surface-tab-active` `#2e2e2e` の上で **4.47**（テキストの 4.5:1 を割る）。
高コントラスト側は周3 で直したが、**既定側は残っている**。

### 原因（判明している場合）

`.tab-bar__tab.is-active`（`color: var(--text-bright)`）と `.tab-bar__tab.is-exited`
（`color: var(--status-exited)`）が**同じ詳細度 (0,2,0)** で、行順だけで後者が勝っている。
つまり 13.58 が 4.47 に黙って置き換わっている。

**これは `design-rules.md`「単一プロパティで複数の状態を表すと、後の状態が前の状態を黙って消す」
が名指しで禁じている型そのもの。**

### 対処方針（design-review で5人中2人が独立に提案）

- [ ] **値ではなく結合状態の規則で解く。** `.tab-bar__tab.is-active.is-exited { color: var(--text-bright) }`
      （詳細度 0,3,0）を足すと、**値を1つも変えずに 4.47 も消える**（白は対 #2e2e2e で 13.58）
- [ ] バッジ（`--status-exited` を直接読む）をどうするかは同時に設計する。
      終了の意味は四角・語・`aria-label` が既に運んでいる

**値を上げる案（`#e09a9a` など）は却下済み。** 対 `--surface-1` で 7.35 となり
`--text-secondary` 7.01 を追い越して「死んだタブが生きているタブより明るい」になる。
加えて1型色覚下で `--text-secondary` と ΔE76 5.8 = 実質同色になる（PR 8 で一度踏んだ失敗の再演）。

### 優先度

P2

### ステータス

未対処（**セレクタの変更なので「値のみ」の周に入らない**。別 Issue に切り出す）

## 5. 正常終了（コード0）でもタブが赤い（severity をタブだけが捨てている）

> **出典**: Issue #134 の design-review（IA / macOS が指摘）

### 症状

`exit` を1回打つと、**画面の左上（タブ）が赤くなり、右上（通知バナー）が青くなる**。
同じ1つのイベントに、逆向きの色が2つ割り当てられている。

| 層 | 正常終了（コード0） | 異常終了 |
|---|---|---|
| 通知バナー | 青（情報） | 赤（エラー） |
| 端末本文 | `終了しました（コード 0）` | `シグナル 9 で終了しました` |
| **タブ** | **赤** | **赤** |

初見ユーザーがこのアプリで最初に赤を見るのは、ほぼ確実に `exit` = 正常終了。
そこで「赤 = 気にしなくていい」を学習すると、本物のエラー（`--status-error`）が
割り引かれて届く。

### 原因（判明している場合）

`severityForExit()`（`src/renderer/src/lib/notices.ts`）は `exitCode` と `signal` を見て
分岐しているのに、`tabAllPanesExited()` は `exit !== undefined` しか見ていない。
**判別に必要なデータは `PaneLeaf.exit` に既にある。**

### 対処方針

- [ ] `--status-exited` を「正常終了（中立色）」と「異常終了（赤）」に分ける
- [ ] 語も分ける（`終了` -> `終了済み` / `終了（コード 1）` / `強制終了`）。
      **`終了` は `${appName} を終了` と同じ語で、`<button role="tab">` の中にあるため
      「押すと終了する」と読める**（IA の指摘）
- [ ] 判定は `severityForExit()` を使い回す（新しい判定を書かない）

### 優先度

P2

### ステータス

未対処（語とトークン分割を伴う構造の変更。別途 design-review が要る）

## 6. `WebglAddon` に `onContextLoss` ハンドラが無い

> **出典**: Issue #134 の design-review（a11y が指摘。配色とは無関係）

### 症状

このアプリは**全タブ・全ペインを同時にマウントしたまま**（`visibility` だけで切り替え）なので、
**WebGL コンテキストがペイン数ぶん同時に生きる**。Chromium の1レンダラあたりの上限は16前後で、
超えると古いコンテキストが黙って失われる。

**そのとき失われたペインは真っ白なキャンバスになるが、支援技術が読む a11y DOM は生き残る。**
読み上げ利用者には見えず、**晴眼の利用者にだけ主コンテンツが消える**、という珍しい向きの不具合。

### 原因（判明している場合）

`grep -rn "onContextLoss" src/renderer/src/` = **0件**。
xterm.js のドキュメントは `addon.onContextLoss(() => addon.dispose())` で
DOM レンダラへ落とすことを明示的に求めている。

### 対処方針

- [ ] `useTerminal.ts` の `WebglAddon` 生成箇所に `onContextLoss` を足し、DOM レンダラへ落とす
- [ ] 落ちたことを観測する手段（S23 が GPU 有効で画素を数えている）を流用できるか検討する

### 優先度

P2

### ステータス

未対処（`/terminal` の領域。#160 の対象外）

## 13. ターミナル内の URL をクリックすると、既定ブラウザではなく Electron の窓が開く

> **出典**: Issue #135 の design-review（power-user が「#135 より優先すべき」と評価）

### 症状

`useTerminal.ts` の `WebLinksAddon` は `window.open(uri, '_blank', ...)` を呼ぶだけで、
**`setWindowOpenHandler` がアプリ全体に0件**。Electron はハンドラ未設定なら
新しい `BrowserWindow` を作るので、**アドレスバーも戻るボタンも無い窓が開く**。

さらに `@xterm/addon-web-links` に `metaKey` / `ctrlKey` / `altKey` の判定が0件で、
**素のクリックで発火する**（iTerm2 / Ghostty は Cmd+クリック）。カーソルを置くつもりの
クリックでも開く。

**脱出コストも高い。** `menu.ts` の「ウィンドウ」サブメニューに `role: 'close'` が無く、
「ペインを閉じる」は `registerAccelerator: false` なので、**その子ウィンドウで `Cmd+W` を
押しても何も起きない**。信号機をマウスで押すしかない。

### 影響（実測に基づく見積もり）

エージェントは PR リンク・localhost・docs を1日中吐く。誤爆1回あたり

## 14. `Cmd+F` が選択範囲を引き継がない（`Cmd+E` を奪ったまま代替が無い）

> **出典**: Issue #135 の design-review（power-user）

### 症状

`toggleSearch` は検索語を1文字も引き継がない（`getSelection` の使用箇所は Renderer に0件）。
一方 `Cmd+E` は macOS 全域の「Use Selection for Find」だが、このアプリは
`last-active-tab` に割り当てている。**奪ったまま、奪った機能の代替が無い。**

現状: 選択 → `Cmd+C` → `Cmd+F` → `Cmd+V` → Enter = 5手。
改善後 2手 = **15〜45手/日**。

### 対処方針

- [ ] `Cmd+F` を開くとき、`term.getSelection()` が空でなければ検索欄に入れる
- [ ] 新しいキーは足さない（`Cmd+E` の割り当ては変えない）

### 優先度

P2

未対処

## 15. ペイン名の編集欄がタブバーに出る（右クリックから始めると視線が飛ぶ）

始まる編集は押した対象の上で始まる（Finder のリネーム）。
