## 4. `CloseTabConfirmDialog` が既定構成で嘘をつく（実測で確定）

### 症状

`src/renderer/src/tabs/CloseTabConfirmDialog.tsx` は次の3つを出す。

```
h2   : 走行中のプロセス {paneCount} 件を終了します
p    : このタブを閉じると、中で動いている {paneCount} 件のプロセスがすべて終了します。
ボタン: 終了する
```

**既定構成（`useTmux: true` + tmux あり）では、これは事実に反する。**

### 実測（2026-08-03。tmux 3.7b・実アプリを agent-browser で操作）

claude タブを閉じるボタンで閉じた後:

- `tmux ls` に **`aiterm-bad7fe3d-… ` が残る**
- `ps` に **`claude --session-id bad7fe3d-… (Ss+)` が生存**

`pty.kill()` が殺すのは tmux **クライアント**だけで、サーバ側のセッションと
中の claude / gemini は生き残る。

### 非対称（`src/main/pty/tmux.ts` が明記）

| | 閉じた後 | 回収経路 |
|---|---|---|
| claude | セッション生存 | 履歴から resume すれば `-A` で同じセッションに当たる（**設計どおり**） |
| gemini | セッション生存 | **アプリからは二度と当たらない**（セッション名が使い捨ての ptyId）。手で `tmux ls` するしかない |

**gemini を使う運用では、タブを閉じるたびに回収不能なプロセスが1本ずつ積み上がる。**

### なぜ今まで見えなかったか

**5 の3箇所の誤記が、この不具合を隠していた。** 「内側が終わっても exit は発火しない」
と信じていれば、「閉じてもプロセスが残る」は永続化の意図どおりに見える。

### 対処方針

**#121 の中で直す**（ユーザー判断。このセッションの方針「新しい Issue を起票しない」）。
文言を `wrappedInTmux` で分岐させる。**判定は純粋関数へ切り出して `test/unit/` で固定する**
（E2E ハーネスは `useTmux: false` 固定なので、そのままでは踏めない）。

**閉じる瞬間に `config.useTmux` を読み直してはいけない。** 設定を後から切った人に、
既に tmux で走っているペインについて嘘をつくことになる。**だから leaf に持つ。**

### ステータス

**対処済み**（周2 後半。`closeTabCopy.ts` + `test/unit/close-tab-copy.test.ts` 16件）

> **1ペインのタブは確認ダイアログが出ない経路が残っている**（`paneCount >= 2` のときだけ出る）。
> gemini タブを1枚で閉じると、いまも無言で回収不能なプロセスが残る。
> **周2 のスコープには入れなかった**（承認された範囲は「ダイアログの嘘を直す」）。
> 6 として別項に切り出した。

## 5. README / PLAN.md / pty-pitfalls.md の tmux の記述が、実測と逆（3箇所）

### 症状

| 箇所 | 書いてあること | 実測 |
|---|---|---|
| `README.md`「tmux 有効時、`claude` を終了してもタブが閉じない」 | 「内側の `claude` が終わっても **tmux セッション自体は生き残る**」 | **偽。** サーバごと終了する |
| `docs/PLAN.md` | 「内側の `claude` が終了しても **`ptyExit` は発火しない**」 | **偽。** 発火する |
| `.claude/skills/terminal/reference/pty-pitfalls.md`「tmux でラップすると PTY の exit が発火しないことがある」 | 「内側の `claude` プロセスが終了しても node-pty の **`onExit` は発火しない**」 | **偽。** 発火する |

### 実測（2026-08-03。tmux 3.7b）

1. `script -q tmux new-session -A -s X -- bash -c '...; exit 0'` は **1秒で返り**、
   `tmux ls` は `no server running`
2. 実アプリで内側の claude（pid 83287）に SIGTERM → **tmux サーバごと終了**し、
   タブは `is-exited` になり**終了バッジが1個出た**

`tmux new-session -A -s X -- cmd` は、cmd が終わるとウィンドウが閉じ、
ウィンドウが無くなればセッションが終わり、クライアントも終了する。**当然の挙動。**

### 正しい記述

- 内側が終わる → セッションも終わる → タブに「終了」が出る（**tmux なしと同じ**）
- **タブを閉じる（クライアントを kill）→ セッションと中のプロセスが生き残る**（4 が本体）

### 対処方針

**3箇所とも書き換える。** `pty-pitfalls.md` は「exit だけに頼るな」という結論まで
誤った前提の上に立っているので、節ごと作り直す。

**実測日と tmux のバージョンを併記する**（この挙動は tmux の実装に依存するため、
将来また変わりうる。「いつ・何で測ったか」が無いと同じ調査をやり直すことになる）。

### ステータス

**対処済み**（周2 後半。3箇所とも実測日 2026-08-03 と tmux 3.7b を併記して書き換えた）

## 6. 1ペインのタブを閉じる経路は、いまも無言で孤児プロセスを作る

### 症状

確認ダイアログは `paneCount >= 2` のときだけ出る（`App.tsx` の `requestCloseTab`）。
**gemini タブを1枚で閉じると確認が出ず、画面にも手がかりが1つも出ないまま、
アプリからは回収できない tmux セッションとプロセスが残る。**

### なぜ周2 で直さなかったか

ユーザーに承認を得た範囲は「**ダイアログが既定構成で嘘をつくのを直す**」だった。
1ペインの経路に確認を新設するのは**振る舞いの追加**で、
タブを閉じるのは 10〜30回/日 の操作なので、確認を増やす判断は独立に要る。

### 選択肢（次の周で決める）

- 回収不能になるケース（tmux + gemini）だけ、1ペインでも確認を出す
- 閉じた**あと**に info の通知バナーを出す（ただし通知に自動消去が無いので、
  出すたびにクリックが1回要る。ヘビーユーザーのレビューで指摘済み）
- 何もしない（README には書いた）

### ステータス

**対処済み**（周5）。**回収不能なものだけ**確認を出す判断にした
（`persistentOrphaned > 0` なら1ペインでも確認する = tmux + gemini）。
claude は履歴から戻れるので止めない。**タブを閉じるのは1日に何十回もある操作なので、
確認は不可逆なものだけに絞る。** 判定に使う内訳は `test/unit/close-tab-copy.test.ts` が固定。
