## 2026-08-03 — 周3: タブの死角（P2 から回った 1）

### 手順を逆にした

**先に S69 を帯へ拡張して赤くしてから直した。** 中央 1点しか見ていない関門では

### 実測（S69 が吐いた地図。非アクティブ・非 hover の 90px のタブ）

```
修正前  0-25 死角(.tab-bar__tab) / 26-76 select / 77-88 死角(.tab-bar__tab)
        = 90px 中 38px（42%）が死角
修正後  0-88 すべて select（右端 1px は border-right）
```

左 26px = `--sp-3`(12) + state-slot(6) + `--sp-2`(8)、右 12px = `--sp-3` と
**トークンの値にちょうど一致した**ので、`::before` をその量だけ外へ伸ばした。

### 途中で見つけたもの

**1枚目のタブの左 4px は `.sidebar__resize-handle` に当たる**（`right: -4px; width: 8px`）。
意図的なつかみ代で `cursor: col-resize` の feedback もあるので受け入れたが、
**タブ自身の死角と混ざる**ので、S69 は3枚開いて真ん中を測る形にした。

### 見た目を1px も変えていない

`::before` は透明で、DOM 構造も変えていない。そのため
**改名中（`.tab-bar__title-input` に差し替わる経路）と state-slot の描画位置に影響しない。**

ただし2つ手当てが要った（どちらも実装中に気づいた）:

- **`.tab-bar__title` に `position: relative`。** 無いと `::before` がタイトルを覆い、
  **ダブルクリック改名が効かなくなる**（`onDoubleClick` はこの span に付いている）
- **`.tab-bar__close` に `z-index: 1`。** `::before` は DOM 順で後に来るので、
  そのままだと閉じるボタンを食う

### design-rules の判断をやり直した

閉じるボタンの左 10px の張り出しは、P2 では**「隣が死角だから無害」**と判定していた。
死角を消したいま、同じ張り出しが**選択領域の上に載る**。

**結論は「残す」だが、理由を差し替えた。** 16-26 は「x」の描画（30-36）のすぐ左＝
**閉じるボタンを狙って外した位置**で、押した結果（閉じる）は狙いと一致する。
上下の張り出しを許しているのと同じ理由。

**`design-rules.md` に「『無害な向き』は、隣を直すと有害に変わりうる」として一般化した。**
根拠に「隣に何も無いこと」を使うと、隣を直した瞬間に失効する。

### 分かったこと: 関門は既にあったが、3つとも間違っていて一度も赤くならなかった

`S56-split-pane.spec.ts` に Issue #67 用の検査は**あった**。`expect.poll` なので
沈黙もしない。それでも `styles.css` の `max-width` をまるごと消して green だった。

| 何を間違えていたか | 実際 |
|---|---|
| **測る場所** | 「1回分割した直後」で測っていた。そのペインは検索バーの自然幅（実測 **252.5px**）より広く、`max-width` の有無で結果が変わらない |
| **測る辺** | 右端を見ていた。`.terminal-search` は `right: var(--sp-2)` で**右端に固定**されており、**右端は構造上けっして越えない**。伸びるのもはみ出すのも**左** |
| **測る対象** | コンテナの `boundingBox()` だけ。`min-width: 0` を外すと**コンテナは `max-width` に収まったまま、中のボタンが箱の外へあふれる** |

**実測（最も細いペイン = 234.25px）:**

| 壊し方 | 旧・関門 | 新・関門 |
|---|---|---|
| `.terminal-search` の `max-width` を消す | **green** | 赤（左へ **26px**） |
| `input` の `min-width: 0` を消す | **green** | 赤（右へ **18px**。コンテナ右端 1192 / 閉じるボタン右端 1218.25 / ペイン右端 1200） |
| 両方あり | green | green |

**「テスト本体が本当に実行されているか」を先に確かめた。** 1.3秒という所要が
8回分割するテストとしては速すぎたので、assert を必ず落ちる値（`< 0`）にして
`Received: 234.25` が出ることを見てから先へ進んだ。**green の理由を
「実行されていない」と取り違えずに済んだ。**

### 直した形

- 検査を**分割が拒否されるまで刻んだ直後**（いちばん細いペイン）へ移した
- `window.evaluate` で**コンテナと全子孫の矩形の和**を取り、ペインの矩形と左右とも比べる
- **「測った条件そのもの」も assert にした**（`expect(paneWidth).toBeLessThan(252)`）。
  ペインが自然幅より広ければ本体の assert は何も守らないので、
  **その前提が崩れたら赤くなる**ようにした
