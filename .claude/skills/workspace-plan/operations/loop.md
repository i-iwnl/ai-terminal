# Loop - 指示からドキュメント更新までを1周する

ユーザーの指示を受けてから「使い方が README に載っている」状態になるまでを、決まった順序で1周させる手順。**この操作の価値は順序ではなく停止条件にある。** 各ステップに「終わったと言ってよい条件」を機械で確認できる形で置き、満たさないまま次へ進まない。

## トリガー

- 機能追加・不具合修正の依頼を受けたとき（規模を問わない）
- `/workspace-plan status` で復元した「次アクション」に着手するとき
- 前の周が終わり、まだ完了条件が残っているとき

引数でIssue番号を受け取れる（`/workspace-plan loop 3`）。省略時は `.claude/workspace/` に1つしかなければそれを使い、複数あればユーザーに確認する（推測しない）。

## 1周の形

```
0. 復元    status で worklog の最新エントリを読む
1. 計画    何を作るか・完了条件・触るファイルを列挙する   ← 確認ゲート
2. 実装    近傍のパターンに合わせて書く
3. 検証    make check（typecheck / lint / unit）→ make e2e
4. 文書    README / docs / skill を実態に合わせる
5. 記録    update で worklog と overview を更新する
                                        ↓
                        完了条件が残っていれば 1 へ戻る
```

戻り先は必ず **1（計画）**。実装の途中から再開しない。前の周で分かったことが次の計画に効くのがループの利点で、そこを飛ばすと同じ設計ミスを繰り返す。

## 各ステップの完了条件

### 0. 復元

- `.claude/workspace/issue-<番号>/worklog.md` の最新エントリの「次に再開するとき最初に読むべきこと」を読んだ
- `overview.md` の完了条件のうち、未達のものを列挙できる

手順は [status.md](status.md)。ワークスペースが無ければ [init.md](init.md) を先に通す。

### 1. 計画（確認ゲート）

**ユーザーの承認を得るまで実装に進まない。** 以下を提示する:

- 今回の周で何を作るか（1周に詰め込みすぎない。検証まで通せる単位に切る）
- 完了条件（**何が観測できたら終わりか**。「実装する」ではなく「E2E の S## が green になる」の形で書く）
- 触るファイルと、`src/shared/ipc.ts` を変更するか（Contract 変更なら `architecture.md` に記録が要る）
- 判断が割れる点（スコープ・保存場所・UI の有無など）は、ここで質問して決める

判断が割れる点が無ければ、承認を待たずに進んでよい。**「決めきれないまま実装を始める」ことだけを禁止する。**

対象範囲に応じて読むべき規約は [init.md](init.md) の表が唯一の正。

#### 見た目を変える周は、ここでペルソナレビューを差し込む

その周が UI の見た目・文言・状態表現を変えるなら、**計画を確定させる前に** [/design-review](../../design-review/SKILL.md) を通す。
起動条件の判定は design-review 側の SKILL.md が唯一の正（ここで列挙し直さない）。

理由は「案が良くなるから」ではない。**1人で書いた案は前提ごと間違っていることがあり、実装後に覆ると全部やり直しになる**から。
過去の実施では、案そのものより先に「デザイン以前に壊れているもの」が5件見つかり、案の中核的な前提が2つ覆った。

レビューの結果、その周のスコープが変わることがある。**変わったら計画に戻る。** 実装に進んでから直さない。

### 2. 実装

- 近傍の既存コードのパターンに合わせた（新しい流儀を持ち込んでいない）
- ルート [CLAUDE.md](../../../../CLAUDE.md) のアーキテクチャの鉄則とコーディング規約に反していない
- 未実装の部分を「実装した」と言っていない

### 3. 検証

順に通す。前が赤いまま次へ進まない。

| 段 | 通すもの | 見るもの |
|---|---|---|
| 型と規約 | `make check` | typecheck / lint / 単体テストが全て通る |
| 振る舞い | `make e2e` | 追加分・既存分ともに green |
| 台帳 | `make e2e-lint` | `FAIL=0`（シナリオと spec が1:1） |

**新しい振る舞いを足したら、テストも足す。** どちらに足すかの分かれ目:

| 対象 | 置き場 |
|---|---|
| 外部に触れない純粋関数（入力→出力が閉じている） | `test/unit/` に vitest |
| 画面・PTY・IPC を跨ぐ振る舞い | `e2e/specs/` に Playwright（追加手順は [/e2e](../../e2e/operations/add-scenario.md)） |

**書いたテストが、対象の不具合で赤くなることまで確認する。** 通ることの確認だけでは、何も検証していないテストを再発防止策として記録してしまう（`issue-1/worklog.md` に実例あり）。

`make e2e` が flaky を出したら、まずマシンの負荷を疑う。テスト設計の問題と誤読しやすい（同じく `issue-1/worklog.md` 参照）。

### 4. 文書

**ユーザーが使えない機能は、作っていないのと同じ。** 追加・変更した機能について、以下のうち該当するものを更新する:

| 変えたもの | 更新先 |
|---|---|
| ユーザーが操作する機能・ショートカット・設定項目 | `README.md` |
| 検証コマンドを増やした / 委譲方針を変えた | ルート `CLAUDE.md` |
| 設計判断・フェーズ計画 | `docs/PLAN.md` |
| skill の手順・知識 | 該当 skill（編集したら `bash .claude/scripts/lint-skills.sh`） |
| UI の規約・閾値・却下した案 | [/design-review](../../design-review/reference/design-rules.md)（**Issue 固有の内容は移さない**） |

**見た目を変えた周は、`docs/images/` の撮り直しが要るかを必ず判定する。**
台帳ハーネスは画像の存在しか見ないので、**中身が古くなっても機械では検出されない**。

README を更新したら、**書いた手順どおりに操作できるかを1度なぞる**（設定項目名・ボタン名・ショートカットが実物と一致しているか）。

### 5. 記録

手順は [update.md](update.md)。このステップを飛ばすと、次の周の「0. 復元」が成立しなくなる。

- `worklog.md` に今周のエントリを追記した（**「次に再開するとき最初に読むべきこと」を省略していない**）
- `overview.md` の完了条件・進捗が実態と一致している
- 今周で見つけた課題を `known-issues.md` に書いた（**「後で書く」にしない。気づいた本人しか書けない**）
- 節目に達していれば Issue / PR に書き戻した（**節目の定義は [update.md](update.md) の表が唯一の正**。ここで列挙し直さない）
- 節目なら、`known-issues.md` の未対処項目を GitHub Issue に起こした -> [promote-known-issues.md](promote-known-issues.md)

**周を閉じる前に、今周で気づいたことが1つも記録されていないなら、それは記録し忘れを疑う。** 検証で赤が出た・仮説が外れた・想定と違う挙動を見た、のいずれも無い周はほとんど無い。

## 停止条件

次のいずれかで**ループを抜ける**。抜けたことをユーザーに明示する。

| 条件 | 抜けたあと |
|---|---|
| `overview.md` の完了条件がすべて達成された | 完了を報告する |
| 同じステップで2周続けて同じ失敗をした | 原因の切り分けをユーザーに提示して判断を仰ぐ |
| 計画ゲートで判断が割れ、ユーザーの回答が要る | 質問して待つ |
| 環境要因（CLI 未インストール、権限、ネットワーク）で先に進めない | `known-issues.md` に記録し、影響範囲を報告する |

**「だいたいできた」で止めない。** 完了条件は観測できる形で書いてあるので、達成の判定は主観にならない。逆に、達成できない完了条件が残ったら、それを黙って落とさず `known-issues.md` に理由付きで残す。

## 途中で止まったとき

セッションが切れた場合の復帰は **0（復元）から**。実装の途中から再開しようとしない。`worklog.md` の最新エントリが「どのステップまで終わったか」を持っているので、そこから該当ステップの完了条件を確認し直す。

worklog に何も書かれていない状態でセッションが切れた場合は、`git status` と `git diff` で実態を確認してから 1（計画）をやり直す。**書きかけのコードを「実装済み」として扱わない。**

## この操作がやらないこと

- **commit / push / PR 作成**: ユーザーの明示指示があるときだけ。ループの一部にしない（ルート CLAUDE.md が唯一の正）
- **Issue の open / close**: `gh issue comment` での書き戻しのみ行う（[update.md](update.md) と同じ方針）
- **複数トラックの並列実装の指揮**: 個人skill `/orchestrator` の担当。このループは単一の流れを1本ずつ回す
