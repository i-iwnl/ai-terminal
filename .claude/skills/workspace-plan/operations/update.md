# Update - 進捗の追記とIssueへの同期

ワークスペースの進捗を反映し、節目でGitHub Issue側にも書き戻す手順。

## 進捗更新ルール（省略不可）

**1つのタスク／ステップが終わるたびに、その都度ワークスペースへ進捗を反映する（作業完了 = ドキュメント更新まで）。** あとでまとめて書く・記憶に頼るのは禁止。「実装した」と書く前に実態を確認し、未実装の項目を完了扱いにしない。

## トリガー

- 実装の進捗を反映したいとき
- 新しい問題や設計変更を記録したいとき
- 実装完了・PR作成・作業完了など節目に達したとき

## 手順

### 1. 現在のワークスペースを特定

`.claude/workspace/issue-<Issue番号>/` の存在を確認する。存在しない場合は `init` を促す。

### 2. 更新対象の特定

状況に応じて、以下のいずれか（または複数）を更新する。

#### worklog.md への作業ログ追記（追記専用）

- 日付 + セクションヘッダ形式で末尾に追記する（過去のログは編集しない）
- 「実施内容」「設計判断」「教訓（該当する場合）」に加え、**「次に再開するとき最初に読むべきこと」を必ず書く**（書式は [worklog-template.md](../reference/worklog-template.md) が唯一の正）。これがセッション断からのコンテキスト復元の要になる。

#### overview.md の進捗反映

- 完成条件チェックリスト・現状進捗テーブル・次アクションを更新する

#### architecture.md の設計変更

- 設計変更があった場合にのみ更新。変更理由を「設計判断履歴」に記録する

#### known-issues.md への問題記録

- 症状・原因・影響範囲・対処方針を構造的に記録し、優先度タグを付ける
- **優先度は必ず書く。** 後で GitHub Issue に起こすとき、優先度ラベルはここの値をそのまま使う（[promote-known-issues.md](promote-known-issues.md)）

### 3. Issueへの書き戻し（節目のみ・省略不可）

**進捗の詳細の唯一の正はワークスペース、状態の唯一の正はIssueのステータスとラベル。** 以下の節目に達したら、要点を1つだけ `gh issue comment` で書き戻す（詳細はワークスペースへのリンクに留め、二重化しない）:

| 節目 | コメント内容の目安 |
|---|---|
| 実装が完了した | 何を実装したか1-2行 + ワークスペースへのリンク |
| PRを作成した | PR番号・URL |
| 作業が完了した | 完了した旨 + 最終ゲート（typecheck/lint）が通った事実 |

```bash
gh issue comment <Issue番号> --body "<要点>"
```

`gh issue close` は行わない（課題が解決したかの判断はユーザーが行う）。

**同じ節目で、`known-issues.md` の未対処項目を GitHub Issue に起こす。** 手順とラベル体系は [promote-known-issues.md](promote-known-issues.md) が唯一の正。ワークスペースに書いたまま放置すると、作業を離れた時点で誰にも見えなくなる。

### 4. 整合性チェック

更新後、以下を確認する:

- `overview.md` の進捗が実態（実装・テストの完了状況）と一致しているか
- `known-issues.md` の対処タスクが `overview.md` の次アクションに反映されているか
- 節目のIssueコメントを書き忘れていないか
