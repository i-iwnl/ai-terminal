# Run Review - デザイン案を5ペルソナにレビューさせる

デザイン案を書き、5体のサブエージェントに並列でレビューさせ、矛盾する指摘を統合して実行可能な案に落とすまでの手順。

**この操作の価値は「多くの意見を集めること」ではなく「案の前提が壊れることを許すこと」にある。**
統合の段階で自分の案を守ろうとすると、レビューを回した意味がなくなる。

## 0. 前提: 先に案を書く

レビュー対象が無い状態でペルソナを起動しない。**批評は対象があって初めて具体になる。**

案には最低限これを含める。含まれていない軸は、レビューでも指摘されずに素通りする。

- 現状の診断（何が問題か。**ファイルパス:行番号の根拠付きで**）
- 設計原則（この案が従う判断基準）
- 提案（A / B / C ... と識別子を振る。**レビュアーが「提案 B に反対」と書けるようにするため**）
- 段階的な導入計画
- 非目標（やらないこと）

案は `.claude/workspace/issue-<番号>/` の外、作業用ディレクトリに置いてよい。**この時点ではリポジトリに入れない**（レビューで覆るため）。

## 1. 5体を並列で起動する

`Agent` ツールで **5体を1メッセージにまとめて起動する**（直列に回すと5倍時間がかかる）。

| subagent_type | 担当する軸 |
|---|---|
| `design-reviewer-macos` | HIG、ウィンドウクローム、メニュー、vibrancy、タイポグラフィのウェイト |
| `design-reviewer-ia` | 初回体験、ラベリング、メンタルモデル、空状態、発見可能性 |
| `design-reviewer-power-user` | 手数、ピクセル予算、キーボード、他ターミナル比較、目の疲れ |
| `design-reviewer-a11y` | WCAG 実測、フォーカス、色覚多様性、VoiceOver、ズーム |
| `design-reviewer-maintainer` | 実装コスト、E2E への影響、PR 分割、鉄則との整合、技術的負債 |

各体に渡すもの:

- **レビュー対象のファイルパス**（案の本体）
- **読んでよいコードの範囲**と、**編集禁止の明示**
- **スクリーンショットのパス**（`docs/images/`。Read ツールで画像として開けることを伝える）
- **既に他レビュアーが確定させた事実**（あれば。再調査を避けて指摘の密度を上げる）

観点の指定は agent 定義側にあるので、**プロンプトで観点を書き直さない**（ドリフトの温床）。渡すのは対象と前提だけ。

### 2周目を回すとき

1周目で確定した事実（例: 「`busy` はエージェント稼働中で確定」）を**全体に配ってから**回す。
同じ調査を5体が別々にやり直すのは無駄で、しかも結論がずれる。

## 2. 指摘を突き合わせる

返ってきた5本を、**指摘した人数**で並べ替える。これが最も重要な操作。

| 人数 | 扱い |
|---|---|
| **3人以上が独立に指摘** | 案の前提が間違っている。**案を直すのではなく、案の前に別の作業として切り出す** |
| 2人 | 採用を既定とし、反対理由があれば書き残す |
| 1人（その人の専門領域） | 採用（その軸の専門家が見つけたもの） |
| 1人（専門外） | 保留。他の軸と衝突しないか確認してから判断 |

### 全員一致の対案でも、そのままは実装しない

**レビュアーの対案には「その時点の他の値」という前提が埋まっている。**
案を統合する過程でこちらが別の箇所を変えると、対案の数値ごと成り立たなくなる。

実例（Issue #20 の Phase 1）。5人全員が「選択中タブを `--surface-3` に畳めば 1.15 -> 1.22 に改善する」と書いたが、
その 1.22 は**ターミナル背景を #1b1b1b に動かす前提**の数値だった。
別のレビュアーの指摘を採ってターミナル背景を据え置いた結果、同じ畳み方をすると **1.13 = 現状より悪化**する。
同様に、全員が推した枠の色 #747474 も、こちらが残したタブの面の上では **2.91** で 3:1 を割った。

したがって:

- **多数決の結論ではなく、その結論を支えている数値を採る。**
- 統合で1つでも値を変えたら、**それに依存する対案を全部計算し直す。** 5人が一致していても関係ない。
- 計算し直した結果レビュアーと違う値になったら、**なぜ違うのかを PR とルールに書く**（次に同じ対案が出るため）。

### レビューが覆すのは「案」だけではない（Issue の完了条件・PR 分割も対象）

**案の外側にあるものも一緒に覆る。** 実例（#149）:

| 覆ったもの | 指摘 |
|---|---|
| **Issue の完了条件の文言** | 「`VoiceOver を検知したため有効です`」が**事実として誤り**（`accessibilitySupportEnabled` は支援技術全般で立つ）。**5人全員** |
| **こちらの PR 分割** | 「PR 1 = 関門だけ（赤いまま main へ）」は**ルート CLAUDE.md の「赤いまま push しない」に反する**。保守 |
| **Issue が書いた「独立」の主張** | 「表示」と「追従」は独立、と本文にあったが、**片方だけ入れると「更新されない生の状態表示」になり、表示そのものの信用を落とす**。macOS / IA |

⛔ **「Issue にそう書いてあるから」で押し切らない。** 完了条件は起票時点の案であって、
**レビューで確定した事実のほうが新しい**（外すときの作法は
[/workspace-plan の loop.md](../../workspace-plan/operations/loop.md) の計画ゲート）。

**矛盾は消さずに、どちらを採るか理由付きで決める。** 実際に衝突した例:

- ヘビーユーザー「サイドバーは既定 0px」 vs macOS デザイナー「サイドバーに vibrancy を入れるのが最大のレバー」
  -> 既定 0px を採り、vibrancy は表示時の見た目として両立させた
- macOS デザイナー「クロームからターミナル配色を導出するのは反対」 vs 初版案「構造的に破綻を防ぐ」
  -> **導出の向きを逆にする**（ターミナル配色からクロームを導く）ことで両方成立させた

## 3. 案を書き直す

**元の案を編集するのではなく、改訂版を別ファイルとして書く。** 何が覆ったかが残る。

改訂版には次を明示する。これが無いと、次に同じ案を思いつく。

- **却下した提案と、その理由**（数値の根拠があるものは数値ごと）
- **初版が誤っていた事実**（レビューで検算されて覆った数字は、必ず正しい値に直す）
- **初版に無かった軸**（レビューで初めて出てきた領域。多くは初回体験とアクセシビリティ）

耐久性のある規約（このアプリで UI を書くとき常に守るもの）に育ったものは、
[../reference/design-rules.md](../reference/design-rules.md) に移す。**Issue 固有の内容は移さない。**

## 完了条件

- [ ] 5体すべてが返ってきた（返ってこなかった体があれば、その軸が空白であることを明示する）
- [ ] 3人以上が指摘した項目を、**案の中ではなく案の前**に切り出した
- [ ] 矛盾した指摘について、どちらを採ったかと理由を書いた
- [ ] 却下した提案に、却下理由を付けた
- [ ] レビューで覆った数字を、案の中で正しい値に直した
- [ ] 耐久性のある規約を `reference/design-rules.md` に反映した

## この操作がやらないこと

- **実装**: レビューは案の段階で回す。実装後に回すと、指摘のたびに書き直しになる
- **GitHub Issue の起票**: [file-proposal.md](file-proposal.md) が担当
- **サブエージェントによる修正**: 5体はすべて読み取り専用。修正はメインが行う
