# File Proposal - レビュー結果を GitHub Issue に起票する

統合済みのデザイン案を GitHub Issue に落とす手順。**チケットの唯一の正は GitHub Issues**（ルート CLAUDE.md）。

## 起票の粒度

**1本にまとめない。** レビューを通した案は、性質の違うものが混ざっている。

| 種類 | 起票先 | ラベル |
|---|---|---|
| デザイン刷新の方針・原則・提案・Phase 計画 | **親 Issue 1本** | `enhancement` + 優先度 |
| 3人以上が指摘した「デザイン以前に壊れているもの」 | **1件につき子 Issue 1本** | `bug` または `enhancement` + 優先度 |
| 案の対象外だが先に決着が要るもの | 親 Issue の末尾に節を作るだけ（起票はユーザーに確認する） | - |

**「デザイン以前に壊れているもの」を親 Issue の中のチェックリストにしない。**
`enhancement` の中に不具合が埋もれ、個別に着手・クローズできなくなる。

ラベル体系の唯一の正は [/workspace-plan promote-known-issues](../../workspace-plan/operations/promote-known-issues.md)。

## 手順

### 1. 親 Issue を先に立てる

子 Issue から親 Issue 番号を参照するため、順序を逆にしない。

本文には次を含める:

- **レビュー体制**（どのペルソナに何の軸を見せたか）。**後から読む人が、この案の視野の広さと限界を判断できるようにするため**
- Phase 0（デザイン以前に直すもの）の一覧と、子 Issue へのリンク
- 設計原則
- 提案（採用・却下を識別子ごとに。**却下したものは却下理由ごと残す**）
- Phase / PR 分割
- 検証方法（見た目の変更で落ちる E2E と、スクリーンショットの撮り直し枚数）
- 非目標

### 2. 子 Issue を立てる

本文の書き方は共通:

- **何が起きているか**（`ファイルパス:行番号` の根拠付き。**推測を書かない**）
- **なぜ優先度が高いか**（手数・影響範囲・支援技術からの不在など、判断できる形で）
- **完了条件**（チェックボックス。「観測できる形」で書く）
- **注意**（この修正で落ちる E2E、触ってはいけない箇所）
- **関連**（親 Issue 番号）

親 Issue 番号は `#PARENT` のようなプレースホルダで下書きし、親の番号が確定してから一括置換する。
**手で書き写すと必ずどれか1本が間違う。**

### 3. 親 Issue に子のリンクを埋め戻す

親の Phase 0 節を、子 Issue 番号入りの表に書き換えて `gh issue edit` で反映する。

### 4. モックアップを作った場合

視覚モックアップ（提案トークンで実際に描いたもの）を作ったら、**親 Issue にコメントとして貼る**。
本文に埋め込まない — 本文は方針の正で、モックアップは更新頻度が違う。

## 完了条件

- [ ] 親 Issue が立ち、レビュー体制が本文に書かれている
- [ ] 「デザイン以前に壊れているもの」が個別の Issue になっている（親のチェックリストになっていない）
- [ ] すべての子 Issue が親を参照し、親がすべての子を参照している（**双方向**）
- [ ] 却下した提案が、却下理由とともに親 Issue に残っている
- [ ] ラベルが付いている（種類 + 優先度）

## この操作がやらないこと

- **Issue の close**: 実装が終わったときにユーザーが判断する
- **ワークスペースの作成**: 起票後、着手するときに [/workspace-plan init](../../workspace-plan/operations/init.md) で作る
- **commit / push / PR 作成**: ユーザーの明示指示があるときだけ（ルート CLAUDE.md が唯一の正）
