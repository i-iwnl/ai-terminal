# Implementation Traps - 実装で繰り返し踏んだ罠

UI を実装するときに、このリポジトリで**実際に作り込んでからレビューで見つかった**罠。
[design-rules.md](design-rules.md) から分割した（案を書くときの規約と、書いたものが壊れる形は
読むタイミングが違う）。**案を書くときも実装するときも読む。**

規約そのもの（原則・閾値・却下済みの案）の唯一の正は [design-rules.md](design-rules.md)。


**すべて実際に作り込んでからレビューで見つかったもの。**

### `--border-subtle` は「区切りを見せる」用途に使えない

| 組み合わせ | 実測 |
|---|---|
| `--border-subtle` 対 `--surface-1` | **1.13** |
| `--border-subtle` 対 `--surface-0` | **1.31** |

**どちらも見えない。** `.tab-bar` の下線が同じ値で実際に見えていないのが証拠。
**線で区切りを見せるなら `--border-control`。** 見せる必要が無いなら余白で区切る
（`.memo-panel__section` の前例）。

「線は増やさない」とコメントに書きながら `border` を足した実例が2回ある。
**コメントと実装が食い違ったら、実装のほうを疑う。**

### 単一プロパティで複数の状態を表すと、後の状態が前の状態を黙って消す

`box-shadow` は上書きされる。アクティブ線（上辺1本）とドロップ枠（4辺）を
同じプロパティで別々に書くと、**両方の状態が重なったとき片方が消える。**

消えるのが `prefers-contrast: more` 側だと、**高コントラストモードの利用者だけが壊れる。**

**結合状態の規則を明示的に書くこと**（`.is-active.is-drop-target` のように）。

### 同じ提案の中の複数の層は、表示条件を揃える

提案 C'（アクティブペインの表現）は3層あり、3層目のペインヘッダは「分割中のみ」だった。
だが2層目のアクセント線は**常時**出ていたため、**1ペインのときも青い線が出て
何も伝えないクロームになっていた**（原則3に違反）。

**片方だけ実装した周では気づけず、全体を見る周で初めて見えた。**
層ごとに「いつ出るか」を表にして、揃っていることを確認する。

### 静的な前提の上に積み上げた保証は、前提を動的にした瞬間に全部消える

Phase 1 の7本は「**すべての段が最も明るい面の上でも 4.5:1 を満たす**」を実測で積み上げた。
この保証は「**面が静的である**」ことに乗っていた。

背景色から面を導出する変更（PR 17）を入れた瞬間、明るい背景で
`--text-primary` 対 `surface3` が **1.23** まで落ちた。

**面や文字を動的にするときは、Phase 1 の保証が生きているかを判定に組み込む**
（`chromeTextRemainsReadable()` のように、割るなら適用しない）。

### `opacity: 0` は3つの性質を持ち、混同しやすい

1. **レイアウトから外れない**（幅を予約したままになる）
2. **アクセシビリティツリーに残る**（VoiceOver は読み上げる）
3. **ポインタイベントを止めない**

`.tab-bar__close` は 3 を `pointer-events: none` で潰し、コメントに
「`opacity` だけで隠すと、非表示のあいだも 24x24 の当たり判定が反応してしまい、
常時表示していた頃と実害が変わらない」と書いてある。
**同じ規則が `.history-item__action` には無く、実際にバグになった**
（絶対配置にした瞬間、タイトル右端のクリックが resume ではなく「編集」に当たる。
9点撃って5点が届かなくなることを実測した）。

**`visibility: hidden` で代用しない。** あれは 1・2・3 をすべて解決するが、
**要素がフォーカスを受けられなくなる**ので `:focus-within` が発火できず、
キーボードからその機能への入口が消える。隠したいものが
「ホバーで出るがキーボードからも到達できるべきもの」なら、
**`opacity: 0` + `pointer-events: none`、hover と `:focus-within` で戻す**が正しい。

### 「幅を予約したまま当たり判定だけ直す」と「幅を回収する」は別物

PR #108（タブの閉じるボタン）を「絶対配置で直した前例」として引くとき、
**何を維持したかを見る。** #108 は `.tab-bar__tab-button` に
`padding-left: calc(14px + var(--sp-2))` を与えて**幅を予約したまま**当たり判定だけ
直したので、描画位置が1px も動かなかった。

同じ手で `.history-item__actions` を絶対配置にすると**96px を回収する**ので、
`text-overflow: ellipsis` の省略位置が動く = **見た目は変わる**。
「#108 と同じ手だから画像は変わらない」は成立しない。

### インラインスタイルは、状態を表すクラス規則に必ず勝つ

`style={{ width }}` を常時付けると `.sidebar.is-collapsed { width: 0 }`（詳細度 0,2,0）が
インライン（1,0,0,0）に負けて**折りたたみが黙って壊れる**。
可変値を JS から渡すときは **CSS カスタムプロパティ経由**にして、
`width: var(--sidebar-width, 260px)` のように書く。そうすれば
`.is-collapsed` の `width: 0` が後勝ちで生きる。

### ドラッグでレイアウトを変えない（ゴースト方式）

`PaneSplitterHandle.tsx` が確立したパターン。**ドラッグ中は
`position: fixed` のゴースト線だけを動かし、実レイアウトは1度も変えない。**
`mouseup` で1回だけコミットする。

これにより ResizeObserver がそもそも発火しないので、
**`fit()` の間引きも `transition` の禁止も要らなくなる**（`pty.resize` は 0 回）。
「ドラッグ中は fit をスキップする」という対症療法より一段上流の解。

**ドラッグ操作にはキーボードの代替を必ず用意する**（WCAG 2.5.7 Dragging Movements）。
`menu.ts` の `分割比を広げる / 狭める / 50%に戻す`（`accelerator: undefined` の
メニュー項目 + 対象への `.focus()`）が前例。**頻度の低い操作にキーを割り当てない**
（`Cmd+英数字` の名前空間は 100手/日級の操作のために空けておく）。

### 「範囲」の見出しと「区切り」の見出しは、見た目を変える

パネル全体のスコープ（1パネルに1つ）と、パネル内のグループ（n 個）を
同じ体裁にすると、**同じ見た目の見出しが縦に並び、1つ目だけ意味が違う**状態になる。

**`text-transform: uppercase` は日本語に効かない**ので、大文字化は区別の手がかりに
数えない（英字が混じるときだけ差が出る）。実効的な手がかりは**下線の有無**。
`.panel-scope` だけが `border-bottom` を持ち、`.task-group__heading` は持たない。

### 密度を変えると、他の spec のクリック位置が動く

`gap` や `padding` を変えると当たり判定の幾何が変わる。
**自分が触っていないファイルのテストが落ちる。**

「isolated では自分の spec は通る、落ちるのは他人の spec だけ」という実測をしても、
**「自分の CSS が他人のテストを落とす」経路を想定していないと帰属を誤る**
（実際に一度誤った）。

### 見た目を変えずに当たり判定だけ直せる

タブの中央が死角だった問題は、**閉じるボタンを `position: absolute` にして
フレックス行から外し、選択用ボタンに `flex: 1` と対応する `padding-left` を与える**ことで、
**描画位置を1px も変えずに**解決した。

**当たり判定の問題を、見た目を変える提案にすり替えないこと。**

### 当たり判定を広げるときは、広げた先が誰のクリック対象かを向きごとに見る

`max(100%, var(--target-size-min))` の `::before` は**四方に等しく**広がる。
**広がった先が「何も起きない死角」か「隣のクリック対象」かで、害がまったく違う。**

Issue #120 B-2 の実測（タブの閉じるボタン。見た目 14x14 / 当たり判定 24x24）:

| 向き | はみ出し | 乗っている先 | 判定 |
|---|---|---|---|
| 左 | 5px | gap の死角（`.tab-bar__tab-button` はその先から始まる） | 無害 |
| **右** | **5px** | **`.tab-bar__tab-button` の `padding-left`**（タイトル文字まであと 3px） | **有害** |
| 上 / 下 | 5px / 4px | `.tab-bar__tab-button` | 無害（下記） |

**規則: 入れ子の破壊的ターゲットは、隣のターゲットへ向かう向きにだけは見た目を越えない。**

- 上下のはみ出しは**そのボタンを狙って外した位置**なので、押した結果（閉じる）は狙いと一致する。残してよい
- 右のはみ出しは**タイトルを狙って外した位置**。押した結果（タブが閉じる = 走行中のエージェントを見失う）は狙いと逆で、しかも破壊的。ここだけを 0 にする
- **`:hover` で出し入れしても解決しない。** CSS の `:hover` はクリックする時点で必ず true なので、当たり判定は**まさに問題になる瞬間に**有効化されている

### 「無害な向き」は、隣を直すと有害に変わりうる（Issue #121 周3 で実際に起きた）

上の表は**左のはみ出し 5px を「gap の死角に乗っているので無害」と判定**していた。
その判定は、**隣が死角であることに依存していた。**

Issue #121 周3 で `.tab-bar__tab` の死角（**90px 中 38px = 42%**）を潰し、
タブの全面を選択領域にした。その瞬間、**同じはみ出しが「選択領域の上」に載った。**

**判定をやり直した結果は「残す」だが、理由は前と違う。**

| | 前の理由 | いまの理由 |
|---|---|---|
| 左のはみ出し（実測 16-26px の 10px） | 隣が死角だから無害 | **「x」の描画（30-36）のすぐ左＝閉じるボタンを狙って外した位置**だから。押した結果（閉じる）は狙いと一致する。上下のはみ出しを許すのと同じ理由 |

**教訓: 「隣が死角だから無害」という判定は、死角を直した瞬間に失効する。**
当たり判定の根拠に「隣に何も無いこと」を使ったら、**その隣を触る変更のときに
必ず読み直す**こと。根拠を「狙いと結果が一致するか」で書いておけば失効しない。

**関門の形も変わった。** `S69` は中央 1点しか見ておらず、42% の死角を
1px も検出しなかった。いまは**幅いっぱいを 1px 刻みで走査**し、
非アクティブなタブでは全列が選択に、アクティブなタブでは全列が
「選択」か「閉じる」のどちらかに解決することを見る。
**「押せるはず」を主張するなら、点ではなく帯で測る。**

**直し方は `::before` をずらすのではなく、ボタンの箱そのものを非対称に広げる。**
`left` を広げたぶんだけ戻し、同じ量を `padding-left` に足すと、
`left + width` が不変なので**描画位置が 1px も動かない**（この不変性はグリフの実測幅に依らない）。
箱が 24px に達すれば `max(100%, ...)` は 100% 側を採り、`::before` は箱と一致する。
**`::before` の中央寄せという前提を壊さないので、`S44-target-size.spec.ts` の
「中心 ± サイズ/2 の四隅」という測り方もそのまま使える。**

**却下した案**（#120 B-2 が挙げていた3案）:

| 案 | 却下の理由 |
|---|---|
| 縦方向にしか広げない | 横を見た目の 14px に戻すと 24x24 を割る。2.5.8 の **spacing 例外も成立しない**（隣接ターゲットとの offset が 24px 未満） |
| タブの高さを上げて実寸 24x24 にする | **問題は横軸。** 縦は 35px のタブに 24px が収まって既に 11px 余っており、高さを上げても誤爆は 1px も減らない。クロームの画素を払って何も買えない |
| 現状のまま許容する | 0px の見た目変更で食い込みを 0 にできるので、許容する理由が無い |

**関門は「24x24 あること」だけでは足りない。** サイズの assert は、隣へ食い込む
壊し方に対して一度も赤くならない。`elementFromPoint` を隣の側へ 1px ずつ振って、
**食い込みが 0 であること**を別の assert として持つ（`S44-target-size.spec.ts`）。

## 支援技術まわりで繰り返し踏んだ罠（#149 / #150）

### live region は「常時マウントして中身を差し替える」。条件マウントは鳴らない

`{detected && <span role="status">…</span>}` は**要素と中身が同時に DOM へ入る**ので、
読み上げが飛ぶことがある。live region は**中身が変わる前から DOM にある**ことが発火の条件。

```tsx
<span className="settings__status" role="status" id={ID}>
  {shouldShow(...) ? TEXT : ''}
</span>
```

**空文字なら行ボックスを作らないので、見た目は「何も出ない」まま**（撮影の画素も動かない）。
このリポジトリの正しい前例は `App.tsx` の `.app-status`（常に1個あり、中身だけ差し替える）。
⛔ **Webhook のテスト送信（`{status.state === 'done' && …}`）を前例にしない。** あれは
ボタン押下直後でフォーカスが手元にあるための特殊ケース。

**この罠は「表示条件」と「読まれない人の集合」が一致するときに最悪化する。**
#149 では、表示が出る条件が「支援技術が動いている」= **読まれない実装に当たる人だけが対象者**だった。

### 説明の文を `<label>` の中に入れない（2つ同時に壊れる）

| 壊れるもの | 何が起きるか |
|---|---|
| **アクセシブル名** | `<label>` の中身は全部コントロールの名前になる。「…読めるようにする **いま有効です。VoiceOver などの…**」と連結し、可視ラベルと名前が一致しなくなる（WCAG 2.5.3 Label in Name） |
| **レイアウト** | `.settings__row` は `grid-template-columns: max-content 1fr` の**2列**。3つ目の子は**2行目の1列目**に落ちて崩れる |

**正解は `</label>` の直後の兄弟要素**（`aria-describedby` でコントロールから参照する）。
前例は `NOTIFY_DEPENDENCY_NOTE_ID`。**インデントもしない** — macOS では入れ子が
「親が off なら無効」を含意し、`.settings__row` の1列目は `max-content` なので空セルでは揃わない。

⚠ **この罠は `SettingsPanel.tsx` のコメントに既に書いてあった**（`= 3.0 秒` の換算表示で一度踏んでいる）。
**それでも5人のレビュアー全員が指摘した** = コメントは、隣に書く人の目に入らない。

### `aria-describedby` は「あると良い」ではなく、無いと目的が達成されない

支援技術の利用者は**コントロールからコントロールへ飛ぶ**（フォームロータ / `VO-Cmd-J`）。
ラベルの外にある静的テキストは、その移動では読まれない。
チェックボックスに来た人が聞くのは「**オフ**」だけで、**説明の存在に気づけない。**

**IDREF は常に固定で書いてよい**（参照先が空でも dangling として無視される）ので、
条件分岐を書かなくてよい。

### アクセシブル名に、括弧・コロン・役割の語を入れない

- **括弧とコロン**: VoiceOver は句読点の読み上げ設定によって「かっこ」「コロン」を**発話しうる**。
  このアプリのアクセシブル名は `、` で繋ぐ（`tabAccessibleLabel` / `paneAccessibleLabel` / `terminalInputLabel`）
- **役割の語**（「入力」「ボタン」「テキストエリア」）: 支援技術が役割を別に読み上げるので**二重に聞こえる**
- **状態を先頭に置く**: `aria-describedby` は名前の直後に読まれるので、
  「…チェックボックス、**オフ**」→「**いま有効です**。…」の順なら矛盾を最短で打ち消せる

### `app.accessibilitySupportEnabled` は「VoiceOver が動いている」ではない

Chromium が**支援技術の利用を検出した**ときに真になる値で、音声コントロール・スイッチコントロール・
AX API に繋ぐ自動化ツールでも立つ。**UI 文言で「VoiceOver を検知」と断定すると、
VoiceOver を起動した覚えのない人に嘘をつく**（しかもその人にとって診断の役に立たない）。

「**VoiceOver などの支援技術**」と例示に留める。⚠ この誤りは `README.md` と Main のコメントにも
同じ形で残っていたので、**直すときは全部まとめて直す**（片方だけ直すと次に触る人が誤ったほうを正とする）。
