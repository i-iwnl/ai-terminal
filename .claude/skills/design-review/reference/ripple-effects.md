# 触ると波及するもの

UI の値や構造を1つ動かしたときに、**どこまで数え直す必要があるか**。
すべて実際に踏んで分かったもので、[design-rules.md](design-rules.md) から切り出した
（同ファイルの行数上限に達したため。**内容は1行も変えていない**）。

### レイアウトを押し下げると、実行中の子プロセスに SIGWINCH が飛ぶ

`.terminal-stack` の高さや幅が変わると
`ResizeObserver -> fitAddon.fit() -> pty.resize() -> node-pty の TIOCSWINSZ -> SIGWINCH` と波及する。

しかも**全タブの `TerminalPane` が同時にマウントされ、非表示タブは `visibility: hidden` でレイアウトを持つ**ため、
`clientWidth === 0` のガードを通過する。**タブ10枚なら1回の変化で `pty.resize` が10回。**

したがって:

- 通知・バナー・パネルの類は**フローに入れず、絶対配置で浮かせる**（`.terminal-search` が既にこのパターン）
- 幅のドラッグ変更は、**ドラッグ中は `fit()` を丸ごとスキップし、mouseup で1回だけ**行う
- `transition: width` を付けない（遷移中に何度も発火し、最終値が `transitionend` まで確定しない）

これは「PTY の出力を加工しない」という鉄則2の**意図**（CLI 側の挙動に干渉しない）に直結する。

### 配色を守るのは S40 / S41。それ以外の E2E は色をほとんど見ていない

E2E にピクセル比較（`toHaveScreenshot`）は無い。**かつては `--text-tertiary` を `#000000` にしても全部 green だった。**
いまは2本が関門になっている:

| spec | 何を守るか |
|---|---|
| S40 | 代表要素のコントラスト比を**実測して数値ごと固定**する（characterization）。既定の配色が黙って動かない |
| S41 | `prefers-contrast: more` で**実際に上がる**こと。テストの無い `@media` は死にコードと変わらない |

**値を変える PR では S40 の期待値の更新が作業の一部**になり、その diff（`3.51 -> 4.67`）がレビュー資料になる。
`getComputedStyle` を読んでいる他の spec も落ちうるので、**どれが該当するかは実際に grep して確認する**（数を暗記しない）。

一方で `docs/images/` のスクリーンショットは**中身が古くなっても機械では検出されない**（台帳ハーネスは存在だけを見る）。
撮り直しは人間の規律で守る。だから 4番目の原則（置換と値変更を分ける）が効く。

**`make e2e-screenshots` は毎回違う画像を出す。** 非決定性が3種類ある:

- **タスク一覧の経過時間**（偽 CLI の `agents.json` は `startedAt` が固定なので撮るたびに増える）
- **セッション UUID がランダム**（ターミナルに `ARGS:` として出る）
- **注釈の配置が反転することがある**（衝突回避の結果。設定ウィンドウで実測）

加えて**フル実行のたびに1件ほど起動 flake が出る**（`--retries` を付けないと
13枚が揃わない）。したがって:

- **撮り直したら RGB で1枚ずつ画素差を測り、「この画面にこの変更が波及するはずがあるか」を言えないものは `git checkout HEAD --` で戻す**
- **`.convert('RGBA')` を挟まない。** Pillow 9.5+ の `getbbox()` は既定 `alpha_only=True` で差分画像のアルファ（全面0）だけを見るため、**目に見えて違う画像でも `None` を返す**
- 「生成した画像がコミット済みと差分ゼロか」を機械で検査する案は、**この非決定性がある限り成立しない**

**測る順序が結果を変えることがある。** 入力欄にフォーカスを当ててから枠を測ると、
`:focus` が `border-color` を変えるので「通常の枠」ではない値が出る。**通常状態を測り終えてからフォーカスする。**

### 色は3箇所に散りやすい

CSS 変数 / 設定 JSON / xterm の `ITheme` に同じ値が散る。

**CSS 変数と TypeScript は統一できない**（Main プロセスから CSS 変数は読めない）。
以前このリポジトリは「揃えてある」というコメントだけで守ろうとして失敗しているので、
**2箇所に置くことを認めたうえで、一致を機械で突き合わせる**:

- 面の値の正は `src/shared/defaults.ts` の `SURFACE`
- CSS の `--surface-*` との一致は `test/unit/css-tokens.test.ts` が検査する
- `BrowserWindow` の `backgroundColor` と E2E ハーネスの theme も、**必ずここから引く**
  （ハーネスが自前の色を持っていたせいで、既定色を変えても撮影に届かない状態が実際にあった）

**xterm の `ITheme` を `getComputedStyle` で CSS 変数から読んではいけない** — CSS が壊れると端末の色が壊れる経路ができ、鉄則2の境界が CSS 側に漏れる。

**ターミナル背景（`--surface-1` / `DEFAULT_THEME.background`）は、動かす理由が無いなら動かさない。**
`.terminal-pane__container` に padding があるため片方だけ変えると外周に帯が出るうえ、
既定テーマの変更・既存 `config.json` の移行・E2E ハーネスの追従が芋づるで付いてくる。

### `color: inherit` の子孫も、そのトークンの消費者として数える

`grep "var(--status-exited)"` は3件しか返さないが、**実際に届いているのは5箇所**だった（Issue #134）。
`.tab-bar__tab.is-exited { color }` を `color: inherit` の子孫が受け継ぐため:

| 見えていた | 隠れていた |
|---|---|
| `.tab-bar__tab.is-exited`（文字色） | `.tab-bar__tab-button`（タイトルの実体） |
| `.tab-bar__state-slot--exited`（塗り） | `.tab-bar__title-input`（**`--surface-3` の上 = このトークンの最明面**） |
| `.tab-bar__exit-badge` | `.tab-bar__close`（`x`。選択中タブでは常時表示） |

**「最も明るい面の上でも検証する」を満たすには、`var(--token)` の grep では足りない。**
`color` を宣言している祖先から `color: inherit` を辿ること。

### `@media (prefers-contrast: more)` で面を変えたら、その面に乗る前景を全部数え直す

Issue #134 の本体はこれだった。`--surface-tab-active` を `#2e2e2e -> #525252` と明るくしたのに
前景を1つも追随させなかったため、**「コントラストを上げる」がその面だけコントラストを下げていた**
（`--status-exited` 4.47 -> 2.57、`--status-your-turn` 6.70 -> 3.86、プロバイダ色3本 3.48〜4.18 -> 2.00〜2.40）。

**壊れるのが高コントラスト側**なので、既定で見ている限り誰も気づかない。
`@media` に面を1行足すたびに、**その面をセレクタで検索して前景を列挙する**こと。

### 強調の順序は、背景ごとの比ではなく前景の相対輝度で決まる

「あなたの番より終了を目立たせない」を守りたいとき、**同じ面に乗るなら比較すべきは前景の輝度**。
`@media` で片方だけ明るくすると順序が入れ替わる。

しかも**片方だけ直せないことがある**: 対 `#525252` で 4.5:1 を満たす色は相対輝度が必ず 0.5547 以上になり、
`--status-your-turn` `#f5a623`（L=0.4681）を確実に超える。
**「順序を保つ」を要件に入れるなら、状態色は組で動かす。**

### コントラスト比の数値を CSS のコメントに書かない

`styles.css` には比の数値が43行あり、**機械が守っているものは1つも無い**。
実際に2件が誤っていた（`4.47` を「4.5:1 も満たす」/ 「S40 が対 `--surface-tab-active` も実測する」）。
**数値ではなく「実測の正は S40」と書く**（`styles.css:73` / `:96` が既に採っている形）。

### characterization の「満たしていない」札は、腐る向きにも検査する

S40 の閾値ループは `if (wcag !== 'pass') continue;`。
**値を直して `ratio` だけ更新し `wcag: 'fail'` を残すと、その項目は緑のまま閾値検査の外に出たきり戻らない。**
「`fail` と書いてあるのに実測が閾値を満たしている」を落とす逆向きの assert を必ず置く。

### 「値を据え置いたから関門も動かない」は、関門が何を測っているかを見るまで言えない

S40 / S41 は `document.querySelector`（**最初の1件**）で対象を選ぶ。
つまり**同じ色を据え置いても、その色が付く要素が変われば測定対象ごと変わる。**

Issue #166 の初版の案は「`--status-exited` の値を据え置くので S40 の 5.49 / 4.47 は動かない」と書き、
**それを根拠に PR を分割していた**。実際には S40 / S41 が測っていた終了マークは
**どちらも `exit`（コード 0）で作った正常終了タブ**のもので、
「正常終了から色を外す」変更はその2件を必ず動かした。

**セレクタが同じでも、そのセレクタに当たる状態を変えたなら、測定対象が変わったかを確認する。**

### 部分一致で語を固定した関門は、語を細分化すると壊れずに恒真化する

`[aria-label*="終了"]` は `終了済み` にも `異常終了` にも `強制終了` にも一致する。
語を severity で分けても**この関門は緑のまま通り続け、何も検査しなくなる**。

**壊れないことが実害。** しかも「関門が赤くなるか確かめる」習慣では見つからない
（そもそも赤くならない）。**語を固定するなら完全一致か、語ごとに別のロケータで数える。**

### 等輝度を許容してよいのは、常時可視の非色手がかりが**その層の外**にあるとき

「原則2 に従えば色は手がかりに数えないので、等輝度でも問題ない」は**循環論法**で、
同じ論法であらゆる等輝度を正当化できてしまう（過去に却下した配色も全部覆せる）。

実際の分かれ目はこれ:

| | 常時可視の代替手がかり | 判定 |
|---|---|---|
| プロバイダの帯（Issue #165） | **無い**。語は `title` = **ホバーして初めて出る** | 等輝度は却下 |
| 終了の severity（Issue #166） | **有る**。バッジの語が常に画面に出ている | 許容できる |

**ツールチップは常時可視に数えない。** そして許容できる場合でも、そこから出る結論は
しばしば「等輝度でよい」ではなく「**その色の層は要らない**」（下記）。

### 白 2px（`--focus-ring`）= その集合の中の現在項目。線は、集合が並ぶ軸に平行な辺に置く

「選択中」を塗りだけで表そうとすると、**このアプリでは必ず 1.4.11 の 3:1 に届かない。**
最前面の面（`--surface-3`）の上ですら、`--text-primary` を保ったまま塗りだけで 3:1 に到達する
無彩色は**存在しない**（`#676767` <= 塗り <= `#717171` が空区間）。塗りで届かせようとすると
**文字色も一緒に動かす**ことになり、そのトークンの意味が薄まる。

したがって、選択中の手がかりは**白 2px の線**で持ち、塗りは冗長な補強に落とす。

| 集合 | 並ぶ軸 | 線を置く辺 |
|---|---|---|
| タブバーのタブ | 水平 | **下辺**（`inset 0 -2px 0`） |
| 縦に並ぶメニュー項目 | 垂直 | **左辺**（`inset 2px 0 0`） |

**向きが違うのは別の意味ではなく、同じ規則の適用結果。**
「白は選択中の唯一の意味なので他に使わない」という禁止は、**この用途を禁じていない**
（roving focus の集合では DOM フォーカスが選択カーソルそのもの = まさに「選択中」）。

⚠ **`box-shadow` は `S40` では測れない**（`measureContrast` は単一プロパティを色として解決する）。
線の色・形は `S78` と同じ形（`boxShadow` 文字列から取る）で別に固定すること。

### 面を明るくするときは、その面が触れている「唯一の境界」を数え直す

浮きもの（メニュー・ポップオーバー）の 1px 枠は、端末出力の上で**そこからが浮きものだと分かる唯一の情報**なので
1.4.11 の対象になる。そして中の行が `width: 100%` なら、**行の塗りは枠に直接接する。**

`--border-control`(#7a7a7a) に対して 3:1 を保てる塗りの上限は **#313131**（3.03）。
つまり **`--surface-3`(#282828) の上で許される段差は 1.133 = 実質ゼロ。**
いま暗い塗り（`--surface-2`）で成立しているのは、**暗い方向へ動いているから**にすぎない。

**明るくするなら、塗りを枠から離す。**
⛔ 行に `margin` を付けて離さない。行が `width: 100%` の flex アイテムだと
**マージンボックスが 100%+2m になり、はみ出す**。**外側（浮きもの本体）に水平 padding を入れる**。
行の左右 padding を同じだけ減らせば**文字の x 座標は動かない**（= 画像も動かない。**実測で確かめる**）。

### 透明な前景を測ると、架空のコントラスト比が出る

`e2e/fixtures/contrast.ts` は前景の alpha を捨てるので、**塗られていない要素を測ると
`rgba(0,0,0,0)` が「黒」として輝度 0 で計算される**（`--surface-3` の上で 1.42）。
**その数字が実在の候補色の実測値と一致することがある**ので、台帳に焼くと確実に誤読される。

いまは `fg[3] === 0` を落としてキーの過不足検査に回している。
**「塗りが当たっていない」は比ではなく `backgroundColor === 'rgba(0, 0, 0, 0)'` で固定する。**
数値の器に非数値の事実を押し込まない。

### 否定形の characterization は、是正の実装方式によって恒真になりうる

「いま壊れている」を固定するとき、**否定形（〜になっていない）で書くと、是正を入れても赤くならないことがある。**

実例（Issue #180 引き継ぎ周5-b）: 「外側クリックのあとフォーカスが `<body>` に落ちている」を固定したが、
是正（`mousedown` のハンドラで `focus()`）を入れても **green のまま**だった。
**`mousedown` の既定動作があとからフォーカスを上書きする**ため。`requestAnimationFrame` で遅らせると戻るが、
**戻る時刻がフレーム境界に依存する**ので否定形の assert は安定しない。

**是正側（肯定形）を `expect.poll` で待つ形にして、是正の PR で足す。**
書いた直後に「これが赤くなる壊し方（= 是正の実装）を1つ挙げられるか」を必ず試すこと。

### 状態を色で分ける前に、「その状態にはピクセルを割かない」を検討する

Issue #166 の初版は「正常終了＝中立色の四角 / 異常終了＝赤い四角」を提案し、
新トークン・`@media` の追随・4面ぶんのコントラスト検算・関門の更新を抱えていた。
しかも高コントラストでは両者が**等輝度に潰れ**（比 1.03）、中立色は
「あなたの番」の橙とも輝度が並んだ（1.50 -> **1.06**。既定側が現状より悪化する）。

**正常終了では四角を出さない**と決めた瞬間に、そのすべてが消えた
（新トークン0本・色の値の変更0本・S40 / S41 の期待値も据え置き）。

**層を1つ減らすほうが、色を1つ増やすより安いことがある。** とくに:

- 「何も起きていない」に近い状態（正常終了・既定値・空）
- 高コントラストで面が明るくなり、前景の選択肢が狭まる層

**判断の材料**: macOS 純正の Terminal.app は正常終了に**ピクセルを1つも割いていない**
（既定で「シェルが正常に終了した場合は閉じる」）。

### 状態を細分化する周は、その語を持っている層を全部数えてから始める

Issue #166 の初版は「終了を表示している層は4層」と書いたが、**実際は6層**だった。
漏れていた2つは、どちらも**支援技術にしか届かない層**:

- `paneHeader.ts` の `paneAccessibleLabel`（分割中の非アクティブなペインの唯一の情報源。
  xterm は WebGL で canvas に描くのでスクロールバックは読み上げに届かない）
- `App.tsx` の `announce`（`role="status"`）

**`grep` する語は、可視テキストだけでなく `aria-label` / `title` / `announce` を含める。**
片方の層だけ細分化すると、同じ1つのイベントについて語彙が2つある状態を新設することになる
（上の「同じ提案の中の複数の層は、表示条件を揃える」と同じ壊れ方）。

### ⛔ スクロールコンテナの中に、外へ出る浮きもの（メニュー・ツールチップ）を置かない

**`overflow-x: auto` を書くと `overflow-y: visible` は `auto` に計算される**（CSS Overflow 3）。
横スクロールのつもりでも**縦にも切られる**。そこに `position: absolute; top: 100%` の
浮きものを置くと、**容器の外へ出た部分が丸ごと消える**。

Issue #170 の実物: `.tab-bar__new-menu`（「+ ▾」のメニュー）の包含ブロックが
`.tab-bar__tabs`（`overflow-x: auto`・高さ 36px）の中にあり、**実機で9点中1点しか当たり判定に出ていなかった**。
さらに開いた瞬間の `focus()` が「見えない要素を見せよう」としてコンテナをスクロールさせ、
**タブのほうが画面外へ押し出されていた**（`scrollTop: 39.5`）。

**この壊れ方は既存の関門を1本も赤くしない。**

| 関門 | なぜ通るか |
|---|---|
| `toBeVisible()` | **祖先のクリッピングを見ない**（矩形が空でなく `visibility` が hidden でなければ可視） |
| 項目のクリック | Playwright が `scrollIntoViewIfNeeded()` を挟むので**切られていても押せる** |
| キーボード操作 | 開いた瞬間に先頭項目へフォーカスが乗るので**見えないまま矢印 + Enter で通る** |

**関門が4本あって、4本とも「見えていない」ことを見ていなかった**（S06 / S64 / S69 / S78）。

したがって:

- **浮きものの祖先に `overflow != visible` を作らない。** 包含ブロックをスクロールコンテナの外へ出す
- **可視性は当たり判定で見る。** `document.elementFromPoint()` が**その浮きものの子孫**に解決すること。
  ⛔ **中心1点で測らない**（中心は3項目の真ん中に当たるので、上下 1/3 のクリップを素通しする）
- **ビューポートに収まっていることも別に見る。** `body { overflow: hidden }` なので、はみ出した分は黙って消える
- 関門は S95（`e2e/specs/S95-new-tab-menu-visible.spec.ts`）

### 浮きものの左右アンカーは、いちばん端に寄ったときの座標で決める

同じ #170 で、クリップを直しただけでは**まだ見えなかった**。原因は3つあり、入れ子はそのうち1つ。

| # | 原因 | 直し方 |
|---|---|---|
| (a) | 祖先のスクロールコンテナに切られる | 包含ブロックを外へ出す |
| (b) | `z-index: 15` が `.notice-list`（**20**）に負ける | 21 へ（モーダルの 30 は超えない） |
| (c) | `left: 0` + `min-width: 160px` で**ウィンドウ右端からはみ出す** | **`right: 0`（右端揃え）** |

(c) は「タブが溢れると `.tab-bar__drag-region`（`flex: 1` / basis 0）の実幅が 0 になり、
アンカーが設定ボタンに密着する」ために起きる。**ウィンドウ幅に依存せず必ず起きる。**

**右端揃えなら、はみ出さないことを算数で言える**（アンカーの右端は最小でもサイドバー 260px + 36px なので
160px は必ず内側）。**JS の座標計算は要らない。** 「動的な座標計算は追従漏れを生むので却下」は
**アンカーの向きを変えることまで否定しない**。

### スクロールコンテナの「端の手がかり」は、そのコンテナの中に置けない

`.tab-bar__tabs` のように `overflow-x: auto` の要素へ `::before` / `::after` を絶対配置すると、
**包含ブロックがスクロール内容なので、帯がコンテンツと一緒に流れて画面外へ出る**
（実測: `scrollLeft = 768` で `left = -184`）。`right: 0` はビューポートの右端ではなく
**スクロール内容の右端**を指す。

⚠ **「スクロールしない行の中にある同じ形」は前例にならない**（`.history-item__actions::before` は
`.history-item` がスクロールコンテナでないから成立している）。移植すると必ず壊れる。

置くなら **(a) スクロールコンテナの外側の要素** か **(b) `mask-image`**（要素ボックスに固定される）。
これは #170 の「`overflow-x: auto` は `overflow-y` も `auto` にする」と**同じ属性が原因の2つ目の罠**。

### タブバーに「スクロールできること」の手がかりを足さない（3人が独立に却下）

**AppKit の `NSTabBar` を実測すると、スクロールバーに 0px しか割いていない**
（`_NSInvisibleScroller` の frame が `y=28 h=0` = タブバーの外に高さ0で置かれている）。
溢れの手がかりは**trailing 端で痩せていくタブそのもの**で、フェードでもスクロールバーでもない。

そして AppKit は**「全部で何があるか」をウィンドウの中では解いていない**。
`NSApp.windowsMenu` に全タブを自動で並べる = **アプリケーションメニュー側で解いている**。

| 案 | 却下理由（**それぞれ別の軸**） |
|---|---|
| 端のフェード | **1.4.11 の 3:1 を構造的に満たせない**（最濃部が背景そのもの = 1.00）。さらに**既に成立している適合を削る**: α 0.26 で本文が 4.5:1 を割り、α 0.67 で白のフォーカスリングが 3:1 を割る。タブが最小幅に張り付いているとき、タイトルに残るのは約 30px（4文字）で、16px の帯はその **53%** を滲ませる |
| 常時スクロールバー（`::-webkit-scrollbar`） | **`::-webkit-scrollbar` に寸法を書いた時点で 2.5.8 の「User agent control」免除が外れる**（4px は 24px を割る）。かつ**非オーバーレイに切り替わってコンテンツボックスを縮める**ので、タブの高さと文字の光学中心が動く（35 -> 31px / 17.5 -> 15.5）。⚠ **サムは選択中タブの塗りには跨らない**（帯はコンテンツボックスの外なので、下は常に `--surface-1`） |
| 手数 | **削減 0手/日。** 到達経路が4重に冗長化されている（`Cmd+1-9` / 折り返す `Cmd+Shift+[` / `Cmd+J` / 通知クリック）。**どれも1〜3手のまま変わらない** |

**代わりに解くなら「ウィンドウ」メニューにタブ一覧を出す**（macOS の作法・**36px を 1px も使わない**・VoiceOver からも読める）。

⛔ **この判断を固定する関門を書かない。** 「手がかりが出ない」を固定する検査は**永久に赤くならない**。
書くなら**メニュー側**（12枚開いて項目が12個ある）に置く。
