# Design Rules - UI を書くとき常に守る規約

ai-terminal のクロームを触るときの判断基準。**個別の刷新案（GitHub Issue）ではなく、案が変わっても残るものだけを置く。**

「何を・なぜやるか」の唯一の正は GitHub Issue、「どう作るか・進捗」は `.claude/workspace/issue-<番号>/`。
ここに書くのは**その両方をまたいで効く規約**だけ。個別 Issue の内容をコピーしない。

## 1. 4つの原則

1. **待たせている状態が、画面のどこを見ていても分かる。**
   通知面はアプリの外（Dock バッジ・OS 通知のクリック遷移）を第0層に置く。
   ウィンドウ内の表現だけで設計すると、**ユーザーが別アプリを見ている時間帯を丸ごと取りこぼす。**

2. **色は情報の補強であって、情報そのものではない。**
   形・位置・語を必ず併記する。**色相の違いは手がかりに数えない**（根拠は下の「3. 閾値」）。

3. **ターミナルが主役。**
   クロームは静かに沈み、状態が変わったときだけ前に出る。クロームに割く横幅の既定は 0px。

4. **トークンで塗る。ただし「置換」と「値の変更」を同じ PR に混ぜない。**
   混ぜると、スクリーンショットが変わった理由が置換ミスなのか意図なのかレビューで分離できない。

## 2. 状態を表す語

`claude agents --json` の `status` の意味は次で確定している。**逆に書かない。**

| 値 | 意味 | 画面に出す語 |
|---|---|---|
| `busy` | エージェント稼働中（人間は待たなくてよい） | **作業中** |
| `busy` 以外 | 人間の入力待ち（あなたの番） | **あなたの番** |
| 未知の値 | CLI が新しい状態を返し始めた | **不明** + 生の値をそのまま表示 |

根拠は `src/main/agents/poller.ts` の遷移検知（`busy -> 非busy` を「作業完了」として通知している）。

**使ってはいけない語:**

- **「待機中」** — 一覧の主語は機械なので「エージェントが待機している＝ヒマ＝放置してよい」と読まれる。意味が真逆になる
- **「実行中」** — ターミナルアプリでは「コマンド実行中」と衝突する
- **CLI の生の英語をラベルとして出すこと** — ただし**メタ情報としては残す**（鉄則4/5「CLI が言ったことを隠さない」、および E2E が検証している）

**二値分岐にしない。** `status === 'busy'` の二値で書くと、CLI が第3の値を返し始めたとき全部が片側に誤訳される。

## 3. 閾値（すべて計算して確認する。目視で判定しない）

| 対象 | 基準 | 見落としやすい点 |
|---|---|---|
| テキスト | 4.5:1（WCAG 1.4.3） | **一番明るい面（モーダル）の上でも検証する。** 暗い面だけで通しても意味がない |
| 非テキスト | 3:1（WCAG 1.4.11） | 入力欄・ボタンの**唯一の境界**になっている枠線、状態のドット・バー、選択状態の塗り |
| フォーカス表示 | 3:1（WCAG 2.4.11。フォーカスの**有無**の差） | **アクセント色は使えないことがある。** 枠を 3:1 に上げると、アクセントと枠の差が縮んで満たせなくなる |
| ターゲットサイズ | 24x24 CSS px（WCAG 2.5.8） | 閉じるボタン類は軒並み割る。**透明な当たり判定で広げる**のが最小コスト |
| ステータス色の上の文字 | 4.5:1 | 白文字は落ちる。**必ず暗色を乗せる** |
| 色覚多様性 | 1型・2型・3型で変換後も区別できる | 位置が同じで**色だけ違う**表現は無効（下記） |

### 数値の正は表ではなく実測（S40）

**紙に書いたコントラストの表は、このリポジトリで3回続けて誤った。**
Issue #20 の A-3、それを引き写した案、その案への「訂正」。
3件とも**計算は合っていて、間違っていたのは「何と比べるか」**だった。

| 実例 | 紙の上 | 実測 |
|---|---|---|
| 設定の入力欄の枠 | 1.50（入力欄**自身の塗り**と比較） | **1.38**（**囲んでいる面**と比較） |
| 検索欄の枠 | 1.71（ターミナル背景と比較） | **1.47**（枠が乗っている**浮いた面**と比較） |
| フォーカスリング | 4.67（枠を上げる**前**の値） | **4.29** |

**枠は2つの色に挟まれており、低いほうが見え方を決める。** どちらの面に乗っているかは DOM の構造で決まるので、
CSS を読んだだけでは判断できない。

したがって:

- **配色の数値を主張するときは、`e2e/specs/S40-contrast-contract.spec.ts` の実測を根拠にする。**
  S40 は `getComputedStyle` で実効色を解決し、**透明でない最初の祖先まで遡って背景を決める**
- 値を変えたら S40 の期待値を更新するのが作業の一部。**推測で書かない**（spec が実測をログに出す）
- 過去の Issue 本文に載っている表は、**設計意図の記録**として読む。値の根拠には使わない

### 信号機ボタンの実測値と、その測り方

**この値は3つの文書に3通り書かれていて、3つとも違った。**
（design-rules「約 68px」/ Issue #20「x16〜84」/ 実測「x16〜76」）

`osascript` + AppleScript-ObjC で `hiddenInset` と同じ `styleMask` の `NSWindow` を作り、
`standardWindowButton` の frame を読んだ結果（**権限不要。`screencapture` は TCC で塞がれる**）:

| ボタン | 実測 |
|---|---|
| close / miniaturize / zoom | いずれも **14 x 14** |
| x 座標 | 9 / 32 / 55（**pitch 23px**） |

Electron は `trafficLightPosition` を **close ボタンの左上**として同じ pitch で並べ直すので、
`{ x: 16, y: 16 }` なら占有領域は **x: 16〜76 / y: 16〜30**（**幅 60px**、光学中心 y=22）。

**信号機はネイティブの `NSButton` で DOM に存在しないため、`getBoundingClientRect()` では測れない。**
当たり判定を主張するなら、**その領域に別の要素が来ていないことを
`document.elementFromPoint()` で確かめる**（`S69-tab-select-center.spec.ts` が同型）。

### ターゲットサイズも紙で計算すると誤る（4件目）

上の3件はコントラストだったが、**同じ型が 2.5.8 のターゲットサイズでも出た。**

| | 紙の上 | 実測 |
|---|---|---|
| `.settings__button`（`試聴` / `テスト送信`） | **22.7〜23.8**（`--fs-xs` 11px × 1.2 + padding 8 + border 2） | **48 x 26.5 / 80.45 x 26.5**（違反していない） |

**行ボックスの高さは `font-size × 行間` にならない。** 日本語を含むシステムフォントスタックでは
`normal` の行送りがフォントのメトリクスで決まり、11px の文字が 16.5px の行ボックスになる。
横幅も、文字数から推定すると必ず外れる。

**要素の実寸を主張するなら `getBoundingClientRect()` で測る。**
`S44-target-size.spec.ts` が既にその形なので、**測りたい要素をそこに足すのが最短。**

**存在しない違反を「直した」とコメントに書かないこと。** 床（`max(100%, 24px)`）として
入れるのは無害だが、**コメントは実測値と「これは是正ではなく床である」を書く。**

### 色覚シミュレーションの結論

Machado (2009) の変換行列で1型（重度1.0）を計算した実測:

| ペア | 通常 | 1型変換後 |
|---|---|---|
| `#f5a623` / `#4caf50` | 1.37:1 | **1.15:1** |
| `#f0a03c` / `#4bb96a` | 1.16:1 | **1.04:1**（輝度差の符号が反転） |

**橙と緑で状態を分ける設計は、色相を変えても改善しない。** 差をつけてよいのは:

- 輝度と占有面積（塗りの有無、バーの高さ）
- 形（実線 / 破線 / 枠線のみ）
- 語（状態語を行の**先頭**に置く。走査は左から右）
- 位置（ソートと、ラベル付きのグループ見出し）

## 4. 触ると波及するもの

### レイアウトを押し下げると、実行中の子プロセスに SIGWINCH が飛ぶ

`.terminal-stack` の高さや幅が変わると
`ResizeObserver -> fitAddon.fit() -> pty.resize() -> node-pty の TIOCSWINSZ -> SIGWINCH` と波及する。

しかも**全タブの `TerminalPane` が同時にマウントされ、非表示タブは `visibility: hidden` でレイアウトを持つ**ため、
`clientWidth === 0` のガードを通過する。**タブ10枚なら1回の変化で `pty.resize` が10回。**

したがって:

- 通知・バナー・パネルの類は**フローに入れず、絶対配置で浮かせる**（`.terminal-search` が既にこのパターン）
- 幅のドラッグ変更は、**ドラッグ中は `fit()` を丸ごとスキップし、mouseup で1回だけ**行う
- `transition: width` を付けない（遷移中に何度も発火し、最終値が `transitionend` まで確定しない）

これは「PTY の出力を加工しない」という鉄則2の**意図**（CLI 側の挙動に干渉しない）に直結する。

### 配色を守るのは S40 / S41。それ以外の E2E は色をほとんど見ていない

E2E にピクセル比較（`toHaveScreenshot`）は無い。**かつては `--text-tertiary` を `#000000` にしても全部 green だった。**
いまは2本が関門になっている:

| spec | 何を守るか |
|---|---|
| S40 | 代表要素のコントラスト比を**実測して数値ごと固定**する（characterization）。既定の配色が黙って動かない |
| S41 | `prefers-contrast: more` で**実際に上がる**こと。テストの無い `@media` は死にコードと変わらない |

**値を変える PR では S40 の期待値の更新が作業の一部**になり、その diff（`3.51 -> 4.67`）がレビュー資料になる。
`getComputedStyle` を読んでいる他の spec も落ちうるので、**どれが該当するかは実際に grep して確認する**（数を暗記しない）。

一方で `docs/images/` のスクリーンショットは**中身が古くなっても機械では検出されない**（台帳ハーネスは存在だけを見る）。
撮り直しは人間の規律で守る。だから 4番目の原則（置換と値変更を分ける）が効く。

**`make e2e-screenshots` は毎回違う画像を出す。** 非決定性が3種類ある:

- **タスク一覧の経過時間**（偽 CLI の `agents.json` は `startedAt` が固定なので撮るたびに増える）
- **セッション UUID がランダム**（ターミナルに `ARGS:` として出る）
- **注釈の配置が反転することがある**（衝突回避の結果。設定ウィンドウで実測）

加えて**フル実行のたびに1件ほど起動 flake が出る**（`--retries` を付けないと
13枚が揃わない）。したがって:

- **撮り直したら RGB で1枚ずつ画素差を測り、「この画面にこの変更が波及するはずがあるか」を言えないものは `git checkout HEAD --` で戻す**
- **`.convert('RGBA')` を挟まない。** Pillow 9.5+ の `getbbox()` は既定 `alpha_only=True` で差分画像のアルファ（全面0）だけを見るため、**目に見えて違う画像でも `None` を返す**
- 「生成した画像がコミット済みと差分ゼロか」を機械で検査する案は、**この非決定性がある限り成立しない**

**測る順序が結果を変えることがある。** 入力欄にフォーカスを当ててから枠を測ると、
`:focus` が `border-color` を変えるので「通常の枠」ではない値が出る。**通常状態を測り終えてからフォーカスする。**

### 色は3箇所に散りやすい

CSS 変数 / 設定 JSON / xterm の `ITheme` に同じ値が散る。

**CSS 変数と TypeScript は統一できない**（Main プロセスから CSS 変数は読めない）。
以前このリポジトリは「揃えてある」というコメントだけで守ろうとして失敗しているので、
**2箇所に置くことを認めたうえで、一致を機械で突き合わせる**:

- 面の値の正は `src/shared/defaults.ts` の `SURFACE`
- CSS の `--surface-*` との一致は `test/unit/css-tokens.test.ts` が検査する
- `BrowserWindow` の `backgroundColor` と E2E ハーネスの theme も、**必ずここから引く**
  （ハーネスが自前の色を持っていたせいで、既定色を変えても撮影に届かない状態が実際にあった）

**xterm の `ITheme` を `getComputedStyle` で CSS 変数から読んではいけない** — CSS が壊れると端末の色が壊れる経路ができ、鉄則2の境界が CSS 側に漏れる。

**ターミナル背景（`--surface-1` / `DEFAULT_THEME.background`）は、動かす理由が無いなら動かさない。**
`.terminal-pane__container` に padding があるため片方だけ変えると外周に帯が出るうえ、
既定テーマの変更・既存 `config.json` の移行・E2E ハーネスの追従が芋づるで付いてくる。

## 5. 却下済みの案（再提案しない）

| 案 | 却下理由 |
|---|---|
| 状態を「左端 3px の色バー」で区別する | 位置が同じで色だけ違うため、色覚特性下で存在しないのと同じ。提案色は**現状より悪化していた** |
| 通知バナーをタブバー直下に押し込む（レイアウトを押し下げる） | 全タブに SIGWINCH が飛ぶ。自動消去だと**ユーザーの操作と無関係にもう一度飛ぶ** |
| タブ先頭に文字マーク（`$` / `C` / `G`）を置く | Mac アプリの語彙ではない。claude と codex がどちらも `C` で破綻する。`$` は zsh の既定プロンプト（`%`）ですらない |
| タブの最小幅を広げる | 8タブで横スクロールに落ち、**タブバー上の状態表示が画面外に出て死ぬ** |
| サイドバーを 44px のレールに畳む | 信号機ボタンがレールをはみ出してターミナル領域に乗る。0px かオーバーレイの二択（**「約 68px」という数字は誤り。実測は下記**） |
| クロームのトークンからターミナル配色を導出する | 「明るいクローム＋暗いターミナル」を常用する層が厚く、破綻ではない。**導出は逆向き**（ターミナル配色からクロームを導く） |
| `prefers-reduced-motion` でグローのパルスを止める | `styles.css` に `transition` / `animation` / `@keyframes` が0箇所。**存在しない動きを止めようとしていた** |
| サイドバーを本文より**明るく**する（macOS の階調に合わせる） | Finder / Mail / Xcode はサイドバーが明るい、という指摘自体は正しい。だが原則3「ターミナルが主役」と衝突し、**一番暗いのは端末であるべき**を優先した。**これは意図的な HIG からの逸脱**として記録する（記録しないと毎回同じ指摘が出る）。ただし「ウィンドウ上端で色が切り替わる継ぎ目が見える」という指摘は実在するので、帯の高さを揃える周で再検討する |
| 選択中タブの塗りを面の段（`--surface-2` / `--surface-3`）に畳む | **畳むと現状より悪化する。** 選択中タブは「奥行き」ではなく「状態」で、値はタブバーとの比で決まる。深さの尺には属さないので、専用トークンで持つ |
| **選択範囲の塗り（`selectionBackground`）を 1.4.11 の 3:1 まで上げる** | **1.4.11 の対象ではない。** 拘束するのは 1.4.3 = 塗りの**上に載るテキスト**。実測で `#264f78` -> `#2f5d8f` は既定前景 `#d4d4d4` を **5.73 -> 4.59** に落とし、ANSI 16 色のうち 3:1 未満が 9 -> 11 色に増える。塗りを 3:1 に届かせる `#3a6ea5` では前景が 3.58 で 1.4.3 を割る。**塗りの 3:1 と文字の 4.5:1 は両立しない**（`selectionForeground` を固定すれば両立するが、選択中だけ ANSI の色が全部潰れる）。`test/unit/selection-contrast.test.ts` がこの両立不能を落ちるテストとして固定している |
| 選択中タブの手がかりをアクセント色（または `--border-control`）の線で足す | `prefers-contrast: more` の面（`#525252`）で **アクセント 2.84 / `--border-control` 1.82** に落ちる。**消えるのが高コントラスト側なので、高コントラストモードの利用者だけが壊れる。** 無彩色の白（`--focus-ring`）は 13.58 / 7.81 で、1〜3型すべてで比が1ミリも動かない。ただし**4辺に回すとフォーカスリング（4辺白）と区別できなくなる**ので下辺のみ |
| フォーカス表示をアクセント色（枠の色替え）で行う | 枠を 1.4.11 の 3:1 に上げると、アクセントと枠の差が **1.70** しか残らず 2.4.11 を満たせない。**フォーカスリングは白**（上限の色なので、面が何であってもコストがゼロ）。`outline-offset` は負にする（`overflow: auto` の親でリングが切られるため） |

## 6. 過去のレビューで判明した、案が落としやすい軸

デザイン案を書くとき、**最初から次を含めておく。** いずれも1人で書いた案から抜け落ちた実績がある。

- **初回起動の体験**（3パネルとも空の状態。状態表現は待つものが0件だと何の役にも立たない）
- **機能への導線が画面上に存在するか**（ショートカット専用になっていないか。メニューバーに載っているか）
- **パネルごとのスコープの違い**（同じ見た目で並んでいるが、範囲・対象・プロバイダが違う）
- **非テキストコントラストとターゲットサイズ**（テキストのコントラストだけ見て終わりがち）
- **アプリを見ていない時間帯**（Dock・OS 通知・ウィンドウ非フォーカス時）
- **フルスクリーンと最小ウィンドウ幅**（既定サイズでしか検証しない案になりがち）

## 7. 実装で繰り返し踏んだ罠（案を書くときも実装するときも読む）

**すべて実際に作り込んでからレビューで見つかったもの。**

### `--border-subtle` は「区切りを見せる」用途に使えない

| 組み合わせ | 実測 |
|---|---|
| `--border-subtle` 対 `--surface-1` | **1.13** |
| `--border-subtle` 対 `--surface-0` | **1.31** |

**どちらも見えない。** `.tab-bar` の下線が同じ値で実際に見えていないのが証拠。
**線で区切りを見せるなら `--border-control`。** 見せる必要が無いなら余白で区切る
（`.memo-panel__section` の前例）。

「線は増やさない」とコメントに書きながら `border` を足した実例が2回ある。
**コメントと実装が食い違ったら、実装のほうを疑う。**

### 単一プロパティで複数の状態を表すと、後の状態が前の状態を黙って消す

`box-shadow` は上書きされる。アクティブ線（上辺1本）とドロップ枠（4辺）を
同じプロパティで別々に書くと、**両方の状態が重なったとき片方が消える。**

消えるのが `prefers-contrast: more` 側だと、**高コントラストモードの利用者だけが壊れる。**

**結合状態の規則を明示的に書くこと**（`.is-active.is-drop-target` のように）。

### 同じ提案の中の複数の層は、表示条件を揃える

提案 C'（アクティブペインの表現）は3層あり、3層目のペインヘッダは「分割中のみ」だった。
だが2層目のアクセント線は**常時**出ていたため、**1ペインのときも青い線が出て
何も伝えないクロームになっていた**（原則3に違反）。

**片方だけ実装した周では気づけず、全体を見る周で初めて見えた。**
層ごとに「いつ出るか」を表にして、揃っていることを確認する。

### 静的な前提の上に積み上げた保証は、前提を動的にした瞬間に全部消える

Phase 1 の7本は「**すべての段が最も明るい面の上でも 4.5:1 を満たす**」を実測で積み上げた。
この保証は「**面が静的である**」ことに乗っていた。

背景色から面を導出する変更（PR 17）を入れた瞬間、明るい背景で
`--text-primary` 対 `surface3` が **1.23** まで落ちた。

**面や文字を動的にするときは、Phase 1 の保証が生きているかを判定に組み込む**
（`chromeTextRemainsReadable()` のように、割るなら適用しない）。

### `opacity: 0` は3つの性質を持ち、混同しやすい

1. **レイアウトから外れない**（幅を予約したままになる）
2. **アクセシビリティツリーに残る**（VoiceOver は読み上げる）
3. **ポインタイベントを止めない**

`.tab-bar__close` は 3 を `pointer-events: none` で潰し、コメントに
「`opacity` だけで隠すと、非表示のあいだも 24x24 の当たり判定が反応してしまい、
常時表示していた頃と実害が変わらない」と書いてある。
**同じ規則が `.history-item__action` には無く、実際にバグになった**
（絶対配置にした瞬間、タイトル右端のクリックが resume ではなく「編集」に当たる。
9点撃って5点が届かなくなることを実測した）。

**`visibility: hidden` で代用しない。** あれは 1・2・3 をすべて解決するが、
**要素がフォーカスを受けられなくなる**ので `:focus-within` が発火できず、
キーボードからその機能への入口が消える。隠したいものが
「ホバーで出るがキーボードからも到達できるべきもの」なら、
**`opacity: 0` + `pointer-events: none`、hover と `:focus-within` で戻す**が正しい。

### 「幅を予約したまま当たり判定だけ直す」と「幅を回収する」は別物

PR #108（タブの閉じるボタン）を「絶対配置で直した前例」として引くとき、
**何を維持したかを見る。** #108 は `.tab-bar__tab-button` に
`padding-left: calc(14px + var(--sp-2))` を与えて**幅を予約したまま**当たり判定だけ
直したので、描画位置が1px も動かなかった。

同じ手で `.history-item__actions` を絶対配置にすると**96px を回収する**ので、
`text-overflow: ellipsis` の省略位置が動く = **見た目は変わる**。
「#108 と同じ手だから画像は変わらない」は成立しない。

### インラインスタイルは、状態を表すクラス規則に必ず勝つ

`style={{ width }}` を常時付けると `.sidebar.is-collapsed { width: 0 }`（詳細度 0,2,0）が
インライン（1,0,0,0）に負けて**折りたたみが黙って壊れる**。
可変値を JS から渡すときは **CSS カスタムプロパティ経由**にして、
`width: var(--sidebar-width, 260px)` のように書く。そうすれば
`.is-collapsed` の `width: 0` が後勝ちで生きる。

### ドラッグでレイアウトを変えない（ゴースト方式）

`PaneSplitterHandle.tsx` が確立したパターン。**ドラッグ中は
`position: fixed` のゴースト線だけを動かし、実レイアウトは1度も変えない。**
`mouseup` で1回だけコミットする。

これにより ResizeObserver がそもそも発火しないので、
**`fit()` の間引きも `transition` の禁止も要らなくなる**（`pty.resize` は 0 回）。
「ドラッグ中は fit をスキップする」という対症療法より一段上流の解。

**ドラッグ操作にはキーボードの代替を必ず用意する**（WCAG 2.5.7 Dragging Movements）。
`menu.ts` の `分割比を広げる / 狭める / 50%に戻す`（`accelerator: undefined` の
メニュー項目 + 対象への `.focus()`）が前例。**頻度の低い操作にキーを割り当てない**
（`Cmd+英数字` の名前空間は 100手/日級の操作のために空けておく）。

### 「範囲」の見出しと「区切り」の見出しは、見た目を変える

パネル全体のスコープ（1パネルに1つ）と、パネル内のグループ（n 個）を
同じ体裁にすると、**同じ見た目の見出しが縦に並び、1つ目だけ意味が違う**状態になる。

**`text-transform: uppercase` は日本語に効かない**ので、大文字化は区別の手がかりに
数えない（英字が混じるときだけ差が出る）。実効的な手がかりは**下線の有無**。
`.panel-scope` だけが `border-bottom` を持ち、`.task-group__heading` は持たない。

### 密度を変えると、他の spec のクリック位置が動く

`gap` や `padding` を変えると当たり判定の幾何が変わる。
**自分が触っていないファイルのテストが落ちる。**

「isolated では自分の spec は通る、落ちるのは他人の spec だけ」という実測をしても、
**「自分の CSS が他人のテストを落とす」経路を想定していないと帰属を誤る**
（実際に一度誤った）。

### 見た目を変えずに当たり判定だけ直せる

タブの中央が死角だった問題は、**閉じるボタンを `position: absolute` にして
フレックス行から外し、選択用ボタンに `flex: 1` と対応する `padding-left` を与える**ことで、
**描画位置を1px も変えずに**解決した。

**当たり判定の問題を、見た目を変える提案にすり替えないこと。**
