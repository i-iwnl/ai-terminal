# AI エージェント隔離実行用サンドボックス

`Dockerfile.sandbox` と `scripts/sandbox.sh` は、AI コーディングエージェント
（`claude`）に危険なコマンドを実行させたいときに、ホストの macOS 環境を壊さない
ようにするための Docker サンドボックスである。

着想元は [receptron/mulmoterminal](https://github.com/receptron/mulmoterminal) の
`Dockerfile.sandbox` / `MULMOTERMINAL_SANDBOX=1` の考え方。

> 開発コンテナ / ビルド CI 用の Docker 環境（`Dockerfile`, `docker-compose.yml`,
> `.devcontainer/`, `.github/workflows/ci.yml`）とは別物。あちらは
> 「ホストで `npm run build` 等を再現する」ためのもので、こちらは
> 「AI エージェントを隔離して動かす」ためのもの。

---

## 1. 何のためのものか

`claude` にリポジトリの操作やスクリプト実行を任せていると、意図しない
ファイル削除・設定変更・システムコマンドの実行などが起きうる。

このサンドボックスは、

- **作業対象のディレクトリだけ**をコンテナにマウントし
- ホストのファイルシステムの他の部分にはコンテナから触れないようにした状態で

`claude` を動かすための環境である。ai-terminal はターミナルアプリなので、
アプリのタブで `./scripts/sandbox.sh` を叩くだけでこのサンドボックスに
入れる、という設計にしている（アプリ本体への機能追加は行っていない。
単なるシェルスクリプトの実行）。

---

## 2. 使い方

```bash
# カレントディレクトリをマウントして起動（ai-terminal のタブでこのまま実行できる）
./scripts/sandbox.sh

# 特定のディレクトリだけをマウントして起動
./scripts/sandbox.sh ~/Desktop/job/some-project

# ヘルプ
./scripts/sandbox.sh --help
```

初回はイメージが無いため自動的にビルドされる（2回目以降はビルド済みのイメージを
そのまま使う）。起動すると、まず**どのディレクトリをマウントしようとしているか**
が画面に表示される。意図したディレクトリであることを確認してから進めること。

Docker がインストールされていない、または Docker Desktop が起動していない場合は
日本語のエラーメッセージが出て終了する。

---

## 3. 認証はどう扱われるか

これが今回の設計で一番重要な論点である。

### 3-1. 確認した事実

このマシン（macOS）の `~/.claude/` 配下を `ls` で確認したところ、
`.credentials.json` のような認証情報とみられるファイルは**存在しなかった**
（ファイル名と存在有無のみ確認。中身は一切見ていない）。

macOS 版の Claude Code CLI は、認証情報をファイルではなく **macOS の
Keychain** に保存していると考えられる。Keychain の中身はファイルとして
コンテナに持ち出せるものではないため、たとえ `~/.claude` をまるごと
コンテナにマウントしても、そこに認証情報のファイルは含まれておらず、
**そのままでは認証を引き継げない**。

### 3-2. 採用した方式

上記の事実に基づき、次の方式を採用した。

- `~/.claude` をホストからそのままマウントする方式は**採らない**
- 代わりに、コンテナ専用の Docker named volume
  （`ai-terminal-sandbox-claude-home`）をコンテナ内の `/home/sandbox/.claude`
  にマウントする
- 初回、コンテナ内で `claude` を起動するとログイン（ブラウザでの OAuth 認証）
  を求められるので、そこでログインする
- ログイン結果はこの named volume に保存されるため、**2回目以降の起動では
  再ログインが不要**になる

つまり「ホストの認証情報を引き継ぐ」のではなく、「コンテナの中で一度だけ
ログインし、その結果をコンテナ専用の場所に永続化する」方式である。

### 3-3. この方式のトレードオフ

- 良い点: ホストの `~/.claude`（全プロジェクトのセッション履歴を含む）を
  一切コンテナに晒さない。サンドボックスとしての隔離性を保てる
- 悪い点: サンドボックスを使うたびに（volume を消さない限りは）再ログイン
  は不要だが、**ホストの `claude` とは別の認証セッションになる**。
  Anthropic 側のサブスクリプションに紐づくログインなので、同じアカウントで
  ログインすれば使えるが、「ホストで一度ログインしたから自動的に使える」
  という体験にはならない

`~/.claude` を丸ごとマウントする方式も技術的には可能だが、その場合
**サンドボックス内から全プロジェクトのセッション履歴（`~/.claude/projects/`
以下）が見えてしまい、隔離の意味が大きく薄れる**。今回はこのトレードオフを
踏まえ、専用 volume 方式を選んだ。

---

## 4. 隔離の限界（正直に書く）

**「サンドボックスだから何をやらせても安全」ということは決してない。**
以下の限界を理解した上で使うこと。

1. **マウントしたディレクトリは保護されない。**
   `-v <ホストのディレクトリ>:/work` でマウントした対象ディレクトリは、
   コンテナ内の `claude` から自由に読み書き・削除できる。隔離されているのは
   「マウントしていないホストの他の部分」だけであり、マウントした
   ディレクトリ自体を壊されるリスクはそのまま残る。

2. **Docker はセキュリティ境界として完全ではない。**
   Docker コンテナは軽量な隔離であり、仮想マシンほど強固な境界ではない。
   カーネルを共有しているため、コンテナエスケープや、Docker
   デーモン・ソケットの誤設定に起因する権限昇格のリスクは一般論として
   存在する。本サンドボックスは「操作ミスやうっかりの破壊的コマンドから
   ホストを守る」ことを目的としており、悪意のあるコードの実行を完全に
   封じ込めるレベルのセキュリティ境界としては設計されていない。

3. **認証情報を持つ named volume のリスク。**
   3章で述べた通り、コンテナ内でのログイン結果は named volume
   （`ai-terminal-sandbox-claude-home`）に永続化される。この volume 自体は
   ホストの Docker 管理下にあるファイルであり、ホスト上で
   root 権限を持つプロセスからは読み取り可能である。また、この volume を
   使う全てのサンドボックス起動が同じ認証セッションを共有する。

4. **ネットワークはデフォルトで有効。**
   `claude` は Anthropic の API と通信する必要があるため、
   `scripts/sandbox.sh` はデフォルトのブリッジネットワークを有効にした
   状態でコンテナを起動する。つまり、コンテナ内のプロセスは（マウントした
   ディレクトリだけでなく）外部のネットワークにもアクセスできる。
   より厳しく制限したい場合は、事前に `claude` へのログインを済ませた上で
   `docker run` に `--network none` を付ける、あるいは許可する通信先を
   プロキシ等で絞る、といった選択肢がある
   （`scripts/sandbox.sh` 内にコメントとして残してある。既定では有効にしている）。

以上より、このサンドボックスは「AI エージェントの操作ミスや、指示した
つもりのない破壊的コマンドからホストの他の部分を守る」ためのものであり、
**マウントしたディレクトリ自体の保護や、悪意のあるコードに対する
強固なセキュリティ境界を提供するものではない。**

## 5. 想定される用途・向かない用途

### 向いている用途

- `claude` にリポジトリ内の探索的な作業やスクリプト実行を任せたいが、
  ホームディレクトリ全体や他のプロジェクトに影響が及ぶのを避けたいとき
- 「このコマンド、本当に実行して大丈夫か」と迷うような操作を、
  使い捨てにできる環境で試したいとき
- 一時的な検証用リポジトリなど、壊れても困らないディレクトリでの作業

### 向いていない用途

- **マウントしたディレクトリ自体を守りたい場合。**
  そのディレクトリは保護されないため、`git` で管理してこまめにコミットする、
  あるいは重要なファイルは別途バックアップするなど、別の手段と併用すること
- **強い悪意を持ったコードやプロンプトインジェクションへの対策として使う場合。**
  Docker の隔離だけでは不十分であり、より強固なサンドボックス
  （VM、gVisor、専用のマネージドサンドボックス環境など）を検討すべき
- **複数人・複数アカウントでの認証情報の共有を想定する場合。**
  named volume は単一の認証セッションを前提にしており、共有運用は
  想定していない
